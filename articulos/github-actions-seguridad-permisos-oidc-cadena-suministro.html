Seguridad en GitHub Actions: permisos mínimos, OIDC y cadena de suministro

Cómo proteger un pipeline de GitHub Actions: permisos mínimos, inyección de scripts, pull_request_target, acciones fijadas por SHA, OIDC con Azure y el caso tj-actions.

Un pipeline de integración y despliegue continuos es, en el fondo, un programa que se ejecuta automáticamente con las llaves de tu infraestructura en el bolsillo. Tiene permiso para escribir en el repositorio, para publicar paquetes, para desplegar en la nube y, a menudo, acceso a contraseñas y tokens. Esa combinación de automatismo y privilegios lo convierte en un objetivo atractivo: ¿para qué atacar una aplicación bien defendida si se puede comprometer el flujo que la construye y la publica?

GitHub Actions es hoy una de las plataformas de CI/CD más usadas, y su modelo de seguridad tiene una peculiaridad que conviene entender desde el principio: un flujo de trabajo combina código propio, código de terceros (las acciones que se reutilizan) y datos que pueden provenir de desconocidos (el título de un issue, el contenido de una pull request abierta desde una bifurcación). Cada una de esas tres fuentes es una puerta de entrada distinta, y la defensa consiste en que ninguna de ellas pueda, por sí sola, llegar a los secretos o escribir en el repositorio.

Este artículo recorre las defensas principales: el GITHUB_TOKEN con permisos mínimos, la gestión de secretos, la inyección de scripts, los desencadenantes privilegiados como pull_request_target, el uso seguro de acciones de terceros (con un caso real documentado por la agencia de ciberseguridad de EE. UU.), la autenticación sin secretos mediante OpenID Connect y los riesgos de los ejecutores autoalojados. Nos apoyamos en la documentación oficial de GitHub y de Microsoft, en un análisis del laboratorio de seguridad de GitHub y en una alerta de CISA. Una advertencia de método: no hemos ejecutado los flujos de ejemplo en un repositorio real ni disponemos de un validador de sintaxis en el equipo de redacción; los fragmentos siguen la sintaxis documentada y se señalan como ilustrativos, y las únicas cifras "vivas" que incluimos (los identificadores de commit de las dos acciones que usa este sitio) se consultaron en la API pública de GitHub el 27 de octubre de 2026. Si quieres ver cómo funciona un flujo de trabajo útil antes de endurecerlo, empieza por nuestro artículo sobre caché en GitHub Actions, y para el contexto de despliegue en la nube, el de Azure Static Web Apps.

Puntos clave
  • El GITHUB_TOKEN debería tener permisos de solo lectura por defecto y ampliarse trabajo por trabajo únicamente donde haga falta; si declaras permissions, los ámbitos que no menciones pasan a none.
  • Cualquier valor externo insertado con ${{ }} dentro de un run: puede convertirse en código: pásalo siempre mediante una variable de entorno intermedia.
  • Combinar pull_request_target con el checkout del código de la PR es una vulnerabilidad clásica ("pwn request"): el código ajeno se ejecuta con permisos y secretos del repositorio destino.
  • Una etiqueta de una acción de terceros puede moverse; fijar la acción por el SHA completo de un commit (o, en vista previa, usar un lockfile) evita que una versión comprometida llegue a tu pipeline sin que lo sepas.
  • OpenID Connect permite autenticarse en la nube con credenciales de corta duración, sin guardar secretos de larga vida en GitHub.
  • El compromiso de tj-actions/changed-files en marzo de 2025 mostró en la práctica cómo una acción popular comprometida puede exponer secretos de miles de repositorios.

El modelo de amenazas de un workflow

Antes de las soluciones conviene tener claro qué se defiende y de quién. Un flujo de trabajo de GitHub Actions maneja, como mínimo, cuatro activos valiosos: los secretos configurados en el repositorio o en el entorno, el token automático con el que el flujo habla con la API de GitHub, el contenido del propio repositorio (que puede modificarse si el token tiene permiso de escritura) y los destinos de despliegue a los que el flujo sabe llegar (un servicio en la nube, un registro de paquetes, un hosting).

Frente a ellos hay varios tipos de atacante, y las defensas de este artículo se ordenan según cuál de ellos contrarrestan:

  • Un contribuyente externo que abre una pull request o un issue con contenido malicioso, ya sea código o texto cuidadosamente construido. Las defensas relevantes son la inyección de scripts y los desencadenantes privilegiados.
  • Un mantenedor comprometido de una acción de terceros, cuyo código se ejecuta dentro de tu flujo con acceso a todo lo que tú le des. La defensa es fijar versiones y limitar los privilegios.
  • Un colaborador con acceso de escritura (o un atacante que ha robado sus credenciales). La documentación recuerda que cualquier usuario con permiso de escritura en el repositorio puede leer todos los secretos configurados, lo que justifica los secretos de entorno con aprobación y las revisiones de cambios en los workflows.
  • Un ejecutor comprometido o reutilizado, un riesgo propio de los ejecutores autoalojados.

Ninguna defensa individual lo cubre todo. La idea rectora es la de mínimo privilegio combinada con defensa en profundidad: si un componente falla (una acción comprometida, una inyección), el daño que puede causar debe estar limitado por los permisos que tenía.

publicidad

El GITHUB_TOKEN y el principio de mínimo privilegio

Cada ejecución de un trabajo dispone de un token de autenticación generado automáticamente, accesible como ${{ secrets.GITHUB_TOKEN }} o mediante el contexto github.token. Se usa para que el flujo hable con la API de GitHub: comentar en una pull request, publicar un paquete, subir resultados de análisis. Según la documentación, sus permisos están limitados al repositorio que contiene el flujo de trabajo, y su vida es corta: caduca cuando termina el trabajo o al alcanzar su vida máxima efectiva, que en los ejecutores alojados por GitHub es de seis horas (el tiempo máximo de un trabajo) y, en los autoalojados, aunque un trabajo puede durar hasta cinco días, el token solo puede renovarse durante un máximo de 24 horas.

Lo importante es qué puede hacer mientras vive. La guía de uso seguro de GitHub recomienda fijar como valor por defecto del token el permiso de solo lectura sobre el contenido del repositorio, y ampliar los permisos trabajo por trabajo únicamente donde sean necesarios. Esa configuración por defecto se establece en los ajustes del repositorio o de la organización; independientemente de ella, cada flujo de trabajo puede (y debería) declarar explícitamente lo que necesita con la clave permissions.

La clave permissions

La referencia de sintaxis de workflows enumera los ámbitos disponibles: actions, artifact-metadata, attestations, checks, code-quality, contents, copilot-requests, deployments, id-token, issues, discussions, packages, pages, pull-requests, security-events, statuses y vulnerability-alerts. La mayoría admite los valores read, write o none; las excepciones son copilot-requests e id-token, que solo admiten write o none, y vulnerability-alerts, que admite read o none.

Dos reglas explican casi todo el comportamiento de esta clave. La primera: si especificas el acceso para cualquiera de estos ámbitos, todos los que no menciones se establecen en none. La segunda: existen atajos, permissions: read-all y permissions: write-all, y la forma permissions: {} desactiva todos los permisos. Que los ámbitos omitidos pasen a none es una gran noticia para la seguridad, porque permite escribir la lista de lo estrictamente necesario y olvidarse de todo lo demás.

yaml 
# Ejemplo ilustrativo (no ejecutado): permisos mínimos a nivel de workflow y de trabajo
name: CI

on:
  pull_request:
  push:
    branches: [main]

permissions: {}            # ningún permiso por defecto para todo el workflow

jobs:
  pruebas:
    runs-on: ubuntu-latest
    permissions:
      contents: read       # solo lo necesario para hacer checkout
    steps:
      - uses: actions/checkout@v7
      - run: ./ejecutar-pruebas.sh

  comentar:
    needs: pruebas
    runs-on: ubuntu-latest
    permissions:
      pull-requests: write # este trabajo sí puede comentar en la PR, y solo eso
    steps:
      - run: echo "Aquí iría la llamada que comenta en la pull request"

Ese ejemplo ilustra el patrón correcto: el workflow completo parte de cero permisos y cada trabajo recibe solo los suyos. Si un paso de pruebas estuviera comprometido (por ejemplo, por una dependencia maliciosa instalada durante las pruebas), el token que tendría en la mano solo permitiría leer el contenido del repositorio, no escribir en él ni tocar las pull requests.

Qué ocurre con las bifurcaciones

Un caso particular importa mucho en los repositorios públicos. Según el análisis del laboratorio de seguridad de GitHub, cuando una pull request procede de una bifurcación (fork) y el workflow se activa con pull_request, el flujo recibe un token de solo lectura y no tiene acceso a los secretos del repositorio. Es una protección deliberada: de lo contrario, cualquier desconocido podría abrir una pull request con un workflow modificado para filtrar los secretos. Veremos en una sección posterior qué pasa cuando se usa un desencadenante distinto que rompe esa protección.

Secretos: guardarlos bien y filtrarlos poco

Los secretos de GitHub (repository secrets, environment secrets y organization secrets) son valores cifrados que el flujo puede leer en tiempo de ejecución. La guía de uso seguro reúne un conjunto de prácticas que merece la pena enumerar con calma, porque la mayoría de las fugas reales vienen de ignorar alguna de ellas.

  • Privilegios mínimos en la credencial. Las credenciales que se guardan como secretos deberían tener solo los permisos que el flujo necesita. La documentación lo justifica con una frase cruda: cualquiera con acceso de escritura al repositorio tiene acceso de lectura a todos los secretos configurados en él.
  • No guardar datos estructurados como secreto. Un secreto no debe ser un bloque de JSON, XML o YAML con varias credenciales dentro, porque el mecanismo de enmascarado depende de reconocer el valor exacto en los registros; un secreto estructurado se reconoce peor. Crea un secreto distinto por cada valor sensible.
  • Enmascarar lo que no sea un secreto de GitHub. Si un valor sensible se genera durante la ejecución o proviene de otra fuente, la instrucción ::add-mask::VALOR hace que se oculte en los registros. No se deben escribir esos valores en el archivo del workflow.
  • Registrar los valores derivados. Un valor que se calcula a partir de un secreto (codificado, transformado, recortado) no se redacta automáticamente. Hay que registrarlo también como secreto o máscara para que se oculte.
  • Reaccionar ante una fuga. La indicación de la documentación es tajante: si un secreto sin redactar llega a un registro de ejecución, hay que eliminar el registro y rotar el secreto, es decir, invalidarlo y generar uno nuevo. Borrar solo el registro no basta, porque otras personas o procesos pueden haberlo copiado mientras estuvo visible.

Secretos de entorno con aprobación

En los repositorios públicos, la documentación de Microsoft sobre la autenticación con Azure recomienda usar secretos de entorno en lugar de secretos de repositorio. Un entorno de GitHub puede exigir la aprobación de revisores antes de que un trabajo acceda a sus secretos: mientras no se apruebe, el trabajo no puede leerlos. Esto crea un punto de control humano antes de que un flujo con permisos sensibles, como un despliegue a producción, pueda ejecutarse, y es especialmente valioso cuando los workflows pueden activarse desde contribuciones externas.

Inyección de scripts: cuando los datos se convierten en código

Esta es probablemente la vulnerabilidad más sutil y más frecuente de los workflows. El problema nace de cómo se procesan las expresiones ${{ ... }}. GitHub evalúa esas expresiones antes de que el paso se ejecute y sustituye el resultado directamente en el texto del script. Si el valor sustituido contiene caracteres con significado para el intérprete (comillas, punto y coma, comandos), puede terminar de forma inadvertida siendo parte del código que se ejecuta.

La documentación de GitHub usa como ejemplo el título de una pull request, github.event.pull_request.title. El mismo razonamiento se aplica a cualquier valor controlado por un tercero: el título o el cuerpo de un issue, un comentario, el nombre de una rama o el mensaje de un commit. Considera este paso, que parece inocente:

yaml 
# VULNERABLE (ejemplo ilustrativo): el título se sustituye dentro del script
- name: Registrar el título
  run: echo "Nueva PR: ${{ github.event.pull_request.title }}"

Si alguien abre una pull request cuyo título contiene una comilla que cierra la cadena y una orden detrás, el texto resultante tras la sustitución es un script distinto del que escribiste, y ese código se ejecuta con los privilegios del flujo, incluidos sus secretos y su token. La cadena de sustitución ocurre antes de que el shell vea nada, de modo que no hay nada que "escapar" de forma fiable a posteriori.

La mitigación: una variable de entorno intermedia

La solución que recomienda la documentación es no usar nunca la expresión dentro del script, sino asignarla a una variable de entorno en el paso y leer esa variable desde el shell. Así, el valor viaja como dato en el entorno del proceso y el shell lo trata como una cadena, sin interpretarla como código:

yaml 
# SEGURO (ejemplo ilustrativo): el valor pasa por el entorno
- name: Registrar el título
  env:
    TITULO: ${{ github.event.pull_request.title }}
  run: echo "Nueva PR: $TITULO"

La guía describe además dos refuerzos. El primero es preferir una acción (por ejemplo, una acción de JavaScript que reciba el valor como argumento) en lugar de un script en línea, de modo que el valor nunca se convierta en parte de un guion de shell generado. El segundo es restringir los permisos del token, para reducir el daño potencial de una explotación, y usar plantillas de análisis de código como las de CodeQL para encontrar patrones vulnerables en los workflows.

Regla práctica. Cada vez que veas ${{ github.event.* }} o cualquier otro valor que pueda escribir alguien ajeno dentro de un bloque run:, trátalo como una alerta. Los valores que controla únicamente el propio repositorio (por ejemplo, un secreto o una constante) no suponen el mismo riesgo, aunque conviene mantener la misma disciplina.

Código no confiable y desencadenantes privilegiados

La tercera familia de problemas tiene que ver con cuándo y con qué contexto se ejecuta un workflow. GitHub ofrece varios desencadenantes para reaccionar a pull requests, y dos de ellos difieren radicalmente en su modelo de seguridad.

pull_request frente a pull_request_target

Según el análisis del laboratorio de seguridad de GitHub:

  • pull_request: para las PR que vienen de una bifurcación, el workflow recibe un token de solo lectura y ningún secreto. Se ejecuta sobre el commit de fusión resultante. Es seguro por diseño porque el código ajeno se ejecuta, pero sin nada valioso a su alcance.
  • pull_request_target: el workflow tiene permiso de escritura y acceso a los secretos del repositorio destino. Se ejecuta en el contexto del repositorio base, no en el de la PR, de modo que por defecto el checkout descarga el código de la rama base, que es código de confianza.

El segundo desencadenante existe por una razón legítima: permite hacer cosas útiles que requieren escritura, como etiquetar una PR o comentar en ella, también para PR de bifurcaciones. El peligro aparece cuando el flujo hace algo más.

El patrón "pwn request"

Una pwn request es, según la definición del laboratorio de seguridad, un ataque en el que una pull request maliciosa desde una bifurcación consigue que un flujo de CI privilegiado ejecute código controlado por el atacante, con lo que este puede obtener acceso de escritura al repositorio o robar secretos. La receta de la vulnerabilidad es la combinación de pull_request_target con un checkout explícito del código de la PR, algo que el artículo califica como una práctica peligrosa que puede llevar al compromiso del repositorio.

Basta con que ese flujo ejecute cualquier cosa que se apoye en el código descargado: una compilación, una instalación de dependencias, un script del propio repositorio. El análisis cita el ejemplo de un paquete de npm malicioso cuyos preinstall o postinstall se ejecutan al instalarlo. Y aunque el flujo no use secretos, el riesgo persiste: el token con permiso de escritura está en memoria y, además, actions/checkout lo guarda en disco por defecto salvo que se indique persist-credentials: false.

yaml 
# PELIGROSO (ejemplo ilustrativo): contexto privilegiado + código de la PR
on: pull_request_target

jobs:
  construir:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
        with:
          ref: ${{ github.event.pull_request.head.sha }}   # descarga el código ajeno
      - run: npm install && npm test                      # lo ejecuta con permisos del repo base

El mismo análisis precisa que tratar el contenido de la PR como datos pasivos, por ejemplo comparándolo o buscando texto sin ejecutar nada, es en general seguro. El riesgo no está en leer el código ajeno sino en ejecutarlo con privilegios.

El patrón seguro: dos workflows separados

La alternativa que recomiendan tanto GitHub como el laboratorio de seguridad es separar el trabajo en dos flujos con un puente de artefactos entre ellos:

  1. Un flujo sin privilegios, activado por pull_request, que compila y prueba el código de la PR. Como no tiene secretos ni escritura, no puede hacer daño. Guarda sus resultados (el número de la PR, un informe de cobertura) como artefactos.
  2. Un flujo con privilegios, activado por workflow_run cuando el primero termina, que descarga los artefactos y actúa sobre ellos, por ejemplo comentando en la PR.

Hay una salvedad crítica que ambas fuentes subrayan: los artefactos que provienen de una PR no confiable son también no confiables. Leer un número o un texto de ellos es aceptable; ejecutar un binario que viene en el artefacto, dentro del flujo privilegiado, reabriría exactamente la misma vulnerabilidad. Además, la guía de GitHub resume la regla general: los flujos que usan pull_request_target o workflow_run no deben hacer checkout explícito de código no confiable, y conviene evitar pull_request_target salvo que el flujo necesite realmente el contexto privilegiado.

Las etiquetas como "puerta" no bastan

Una solución popular es exigir que un mantenedor ponga una etiqueta (por ejemplo, "safe to test") antes de ejecutar el flujo sobre el código de la PR. El laboratorio de seguridad la acepta únicamente como parche temporal, y explica por qué es frágil: existe una condición de carrera entre la aprobación y la ejecución. Un atacante puede subir un commit nuevo después de que el mantenedor revise el código y ponga la etiqueta, pero antes de que el flujo se inicie, de modo que se ejecuta código que nadie revisó. El análisis aconseja también cerrar o rebasar las PR abiertas antes de corregir el flujo, porque esas siguen ejecutando la versión antigua del workflow.

Acciones de terceros: la cadena de suministro

La reutilización de acciones es la gran ventaja de Actions: una línea uses: otro/repositorio@version incorpora capacidades completas sin escribirlas. Pero cada acción de terceros es código que se ejecuta con tus permisos. La guía de uso seguro lo dice sin rodeos: una acción comprometida tendría acceso a todos los secretos configurados en tu repositorio y, posiblemente, podría usar el GITHUB_TOKEN para escribir en él. Esa es la definición de un ataque a la cadena de suministro.

Las etiquetas se pueden mover

La forma habitual de referenciar una acción es por etiqueta (@v4) o por rama (@main). La documentación de GitHub avisa del problema: una etiqueta puede moverse o borrarse si un atacante consigue acceso al repositorio donde vive la acción. Si el atacante repunta la etiqueta hacia un commit malicioso, todos los flujos que la usan ejecutarán el código modificado la próxima vez que se activen, sin que nadie haya cambiado una sola línea en los repositorios que las consumen. Un tag es una promesa; un SHA es un hecho.

Fijar por SHA

La medida clásica es referenciar la acción por el hash completo de un commit, que es inmutable. La guía recomienda fijar las referencias a un SHA de commit, con una precaución: comprobar que el SHA procede del repositorio original de la acción y no de una bifurcación. También aconseja revisar el código fuente de la acción para confirmar que trata tu contenido y tus secretos como esperas. En la práctica, se acompaña el SHA con un comentario con la versión legible, para que las revisiones y las herramientas de actualización sepan a qué corresponde.

Para este mismo sitio, que se despliega con GitHub Actions hacia Azure Static Web Apps, los commits vigentes el 27 de octubre de 2026 de las etiquetas que usa el flujo, consultados en la API de GitHub, eran los siguientes. Verifícalos tú mismo antes de copiarlos, porque la etiqueta v1 de la acción de despliegue es una etiqueta de versión mayor que puede avanzar:

yaml 
# Ejemplo ilustrativo (no ejecutado): acciones fijadas por SHA con la versión en un comentario
steps:
  - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1  # v7.0.1
    with:
      persist-credentials: false
  - uses: Azure/static-web-apps-deploy@4d27395796ac319302594769cfe812bd207490b1  # v1
    with:
      azure_static_web_apps_api_token: ${{ secrets.TOKEN_DE_DESPLIEGUE }}
      action: "upload"
      app_location: "/"

Fijar por SHA tiene un coste: dejas de recibir las actualizaciones automáticas de seguridad que traería una etiqueta móvil, así que necesitas un mecanismo de actualización. La documentación sugiere usar Dependabot para mantener actualizadas las referencias a las acciones, con una sutileza que conviene conocer: Dependabot no genera alertas de seguridad para las acciones fijadas por valores SHA, de modo que las actualizaciones de versión (no las alertas) son lo que mantiene ese tipo de referencias al día.

Políticas de la organización: bloquear y exigir SHA

Desde el 15 de agosto de 2025, la política de acciones permitidas de GitHub admite dos controles nuevos, según su registro de cambios. El primero es el bloqueo explícito: se antepone un signo ! a una entrada de la lista para bloquear una acción o una versión concreta, y esa lista de bloqueo se comprueba al final, de modo que prevalece sobre cualquier otra regla que la permitiera. El segundo es la obligatoriedad del SHA: los administradores pueden exigir que los workflows fijen las acciones por el SHA completo de un commit, y cualquier workflow que intente usar una acción sin fijar falla. Ambos se configuran en la política de acciones permitidas a nivel de empresa, organización o repositorio.

Esa política convierte la buena práctica en una regla verificable: en lugar de confiar en que cada colaborador fije sus acciones, el sistema rechaza los workflows que no lo hacen. Es la diferencia entre una recomendación y un control.

Lockfiles de dependencias de workflows (vista previa)

La guía de uso seguro de GitHub contiene una afirmación que cambia el panorama a medio plazo: la mejor medida es bloquear las dependencias del workflow con un lockfile, algo que describe como la protección más fuerte disponible y que, según la página, sustituye al fijado por SHA para los repositorios que lo adopten. La página conceptual dedicada a estos archivos aporta los detalles:

  • Se guardan en .github/workflows/actions.lock, dentro del repositorio, y los genera la extensión de la CLI de GitHub gh actions-lock. El archivo es generado por máquina y no debe editarse a mano.
  • Registran, para cada dependencia, la referencia original (etiqueta o rama), el SHA resuelto del commit y los identificadores numéricos del propietario y del repositorio de origen (owner_id y repo_id).
  • Cubren también las dependencias transitivas, es decir, las acciones que usan las acciones que tú usas, con la excepción de las llamadas a workflows reutilizables.
  • En tiempo de ejecución, GitHub exige que cada dependencia de un workflow incorporado al lockfile esté presente en él, ejecuta el commit bloqueado (que es también el que comprueban las políticas de acciones permitidas) y usa los identificadores de propietario y repositorio para confirmar que el repositorio detrás de un nombre sigue siendo el que bloqueaste.

Esa última comprobación cubre un escenario que el fijado por SHA no contempla: que el nombre de un repositorio pase a apuntar a un repositorio distinto. La documentación solo dice que los identificadores numéricos sirven para confirmar que el repositorio que hay detrás de un nombre sigue siendo el que bloqueaste; el ejemplo concreto de una cuenta que se borra y cuyo nombre registra otra persona es un razonamiento nuestro sobre cómo podría ocurrir, no un caso descrito en la fuente. Pero hay que ser prudente: la propia documentación indica que los lockfiles de dependencias de workflows están en vista previa pública y sujetos a cambios, y no precisa cuándo serán de disponibilidad general ni qué planes los incluyen. Es una dirección prometedora, no un estándar consolidado, y por eso en este artículo el fijado por SHA sigue siendo la recomendación práctica de base.

Revisión de cambios en los workflows

Una defensa organizativa sencilla y eficaz: añadir .github/workflows al archivo CODEOWNERS, de modo que cualquier cambio en los workflows requiera la aprobación de un revisor designado. Así, un colaborador (o alguien que haya robado sus credenciales) no puede modificar un flujo para filtrar secretos sin que otra persona lo vea. La guía menciona además las puntuaciones de OpenSSF Scorecards, una herramienta que señala prácticas arriesgadas de la cadena de suministro, entre ellas la inyección de scripts, los permisos del token y las acciones sin fijar.

Un caso real: tj-actions/changed-files

Los riesgos anteriores no son teóricos. En marzo de 2025, la agencia de ciberseguridad de Estados Unidos (CISA) publicó una alerta sobre el compromiso de una acción muy popular: tj-actions/changed-files (identificada como CVE-2025-30066), que usan miles de repositorios para saber qué archivos han cambiado en una pull request. Según la alerta, el compromiso permitió la divulgación de secretos, entre ellos claves de acceso, tokens personales de GitHub, tokens de npm y claves RSA privadas.

Los datos concretos de la alerta merecen ser leídos con atención:

  • Ventana de exposición. CISA indicó que las organizaciones debían auditar el uso de la acción entre las 00:00 UTC del 12 de marzo de 2025 y las 12:00 UTC del 15 de marzo de 2025, y que debían revisarse todas las versiones de la acción en ese periodo, porque la alerta no precisa qué etiquetas se vieron afectadas.
  • Un segundo compromiso relacionado. La alerta señala que el compromiso de tj-actions/changed-files pudo haberse facilitado por el de otra acción, reviewdog/action-setup@v1 (CVE-2025-30154), ocurrido aproximadamente al mismo tiempo (el 11 de marzo de 2025, entre las 18:42 y las 20:31 UTC). Enumera además otras acciones de ese mismo ecosistema que podían estar afectadas, entre ellas reviewdog/action-shellcheck, action-composite-template, action-staticcheck, action-ast-grep y action-typos.
  • La corrección. La vulnerabilidad se corrigió en la versión 46.0.1, y para el componente de reviewdog se indicó actualizar a un commit concreto o seguir las instrucciones de GitHub.
  • Qué hacer. CISA pidió rotar de inmediato todos los secretos identificados "porque deben considerarse comprometidos", y revisar los registros de los repositorios cuyos workflows ejecutaron el commit malicioso. La alerta advierte de que el contenido filtrado podía estar ofuscado como una carga con doble codificación en base64. La alerta se publicó el 18 de marzo de 2025, según su dirección, y se revisó por última vez el 26 de marzo.

Qué enseña este caso (y qué no)

La lección técnica es la que ya hemos visto: confiar en una etiqueta móvil equivale a ejecutar lo que su propietario (o quien le robe el acceso) decida mañana. Quien referenciaba la acción por etiqueta ejecutó el código modificado sin cambiar nada en su repositorio; quien la tenía fijada por SHA no habría recibido el commit malicioso.

Hay que ser rigurosos sobre un matiz: la alerta de CISA que hemos consultado no recomienda expresamente fijar las acciones por SHA, ni describe el mecanismo interno del código malicioso más allá de la divulgación de secretos. La recomendación de fijar por SHA procede de la guía de uso seguro de GitHub, que es la que hemos citado, y el vínculo con este caso es una inferencia razonable, no una conclusión de la alerta. Del mismo modo, la rotación de secretos que pide CISA es la medida de contención que sigue siendo necesaria, incluso para quien hubiera fijado versiones, si ejecutó un flujo con el commit malicioso en ese periodo.

OpenID Connect: autenticarse sin guardar secretos

Otro frente de riesgo son las credenciales de larga duración que se guardan como secretos para desplegar en la nube. Si se filtran (por una acción comprometida, por una inyección, por un registro mal protegido), el atacante puede usarlas desde cualquier lugar hasta que se rotan. La alternativa moderna es OpenID Connect (OIDC), que la documentación de GitHub presenta con una motivación clara: no hace falta duplicar las credenciales de la nube como secretos de larga duración en GitHub, y los tokens que se emiten son de corta vida y se renuevan automáticamente.

Cómo funciona el flujo

  1. Relación de confianza. En el proveedor de nube se configura que ciertos flujos de GitHub pueden solicitar acceso a un rol o identidad concretos.
  2. Un token por ejecución. Para cada trabajo, el proveedor OIDC de GitHub genera un token web JSON (JWT) con reclamaciones que identifican el flujo.
  3. Solicitud. Un paso o acción del trabajo pide ese token y se lo presenta al proveedor de nube.
  4. Validación y emisión. La nube valida las reclamaciones contra las condiciones de confianza y, si coinciden, emite un token de acceso de corta duración disponible solo durante el trabajo.

Las reclamaciones del token son las que permiten escribir condiciones precisas. La documentación muestra, entre otras, sub (el sujeto), aud (la audiencia), iss (el emisor, https://token.actions.githubusercontent.com), repository, ref, environment y job_workflow_ref (la referencia al workflow reutilizable). Para el sujeto presenta formatos como repo:ORG/REPO:ref:refs/heads/main, que identifica una rama de un repositorio, y repo:ORG/REPO:environment:NOMBRE, que identifica un entorno. La buena práctica, que se deduce del propio diseño, es que la condición de confianza sea lo más estrecha posible: una identidad de despliegue vinculada a un entorno concreto con aprobación manual es mucho más segura que una vinculada a todo el repositorio.

El permiso id-token

Para que un flujo pueda pedir el token OIDC necesita el permiso id-token: write. La referencia de sintaxis lo confirma: establecer ese ámbito en write permite al flujo obtener un token OpenID Connect. Es un ámbito aparte del resto precisamente para que se conceda de forma explícita y solo donde haga falta.

Un ejemplo con Azure

La documentación de Microsoft describe cómo conectar GitHub Actions con Azure por este método. El requisito previo es configurar una credencial de identidad federada en una aplicación de Microsoft Entra (con su entidad de servicio) o en una identidad administrada asignada por el usuario, de modo que confíe en los tokens que emite GitHub Actions para tu repositorio. Después se guardan tres valores como secretos: AZURE_CLIENT_ID, AZURE_TENANT_ID y AZURE_SUBSCRIPTION_ID, que son identificadores de la aplicación, del directorio y de la suscripción; la propia documentación recomienda, para mejorar la seguridad en repositorios públicos, usar secretos de entorno en lugar de secretos de repositorio. El flujo usa la acción de inicio de sesión de Azure:

yaml 
# Basado en el ejemplo de la documentación de Microsoft (ilustrativo, no ejecutado aquí)
name: Despliegue con OIDC
on: [push]

jobs:
  desplegar:
    runs-on: ubuntu-latest
    permissions:
      id-token: write    # necesario para pedir el token OIDC
      contents: read
    steps:
      - name: Iniciar sesión en Azure
        uses: azure/login@v2
        with:
          client-id: ${{ secrets.AZURE_CLIENT_ID }}
          tenant-id: ${{ secrets.AZURE_TENANT_ID }}
          subscription-id: ${{ secrets.AZURE_SUBSCRIPTION_ID }}

      - name: Ejecutar un comando de Azure CLI
        uses: azure/cli@v2
        with:
          azcliversion: latest
          inlineScript: |
            az account show

Fíjate en que no aparece ninguna contraseña ni ningún secreto de cliente: la acción obtiene el token OIDC del trabajo y lo intercambia por un token de Azure válido solo mientras dure la ejecución. La acción de inicio de sesión admite además un parámetro opcional de audiencia, cuyo valor por defecto en las nubes públicas es api://AzureADTokenExchange. Nota que este ejemplo usa etiquetas (@v2); aplica sobre ellas lo dicho antes sobre fijar por SHA.

Este es el mismo principio que mencionábamos en nuestro artículo sobre Terraform y la automatización en Azure al hablar de GitOps: la identidad con la que el flujo despliega la infraestructura debería ser una identidad federada y no una contraseña guardada. Los tipos de entidad que se pueden usar al crear la credencial federada en Azure (entorno, rama, pull request o etiqueta) son un detalle del proceso de configuración en Azure que damos aquí como conocimiento general, porque no aparecía en el texto de la documentación que consultamos.

Ejecutores autoalojados

Los ejecutores alojados por GitHub se crean limpios para cada trabajo y se destruyen al terminar. Los ejecutores autoalojados (self-hosted runners) son máquinas tuyas que ejecutan trabajos, y la documentación de GitHub es muy clara sobre sus riesgos:

  • En repositorios públicos casi nunca deberían usarse. Cualquier usuario puede abrir una pull request que ejecute código en ellos y comprometer el entorno.
  • No garantizan un entorno limpio. Un ejecutor autoalojado no tiene por qué ser efímero, así que código no confiable puede comprometerlo de forma persistente y afectar a trabajos posteriores. Los ejecutores alojados por GitHub sí ofrecen ese aislamiento.
  • La exposición se comparte. Los ejecutores de organización o de empresa pueden ejecutar trabajos de varios repositorios, por lo que un compromiso tiene un alcance amplio. Los grupos de ejecutores ayudan a limitarlo.
  • Mitigaciones imperfectas. Los ejecutores efímeros "just-in-time" ayudan, pero no garantizan un trabajo por ejecutor. Y los secretos pasados como argumentos de línea de comandos pueden ser visibles para otros trabajos de la misma máquina.

Cómo queda este sitio

Para aterrizar todo lo anterior, miremos el caso del propio repositorio que aloja esta página, que es público y se despliega con un flujo generado por Azure Static Web Apps. Su estructura es la habitual: se activa con push a main y con pull requests, usa actions/checkout y Azure/static-web-apps-deploy referenciadas por etiqueta, y recibe el token de despliegue de Azure como secreto. Aplicando lo que hemos visto, un análisis honesto señala lo siguiente:

  • Etiquetas en lugar de SHA. Ambas acciones están referenciadas por etiqueta. Es lo más recomendable corregir, con los SHA mostrados arriba como punto de partida (a verificar).
  • Permisos del token. El flujo no declara permissions, de modo que depende del valor por defecto del repositorio. Declarar un bloque explícito, con contents: read como base, reduciría el daño de un compromiso; la acción de despliegue usa el GITHUB_TOKEN para integraciones como comentarios en pull requests, así que habría que probar qué permisos adicionales necesita antes de cerrarlos del todo. No hemos probado ese ajuste, y lo presentamos como una línea de trabajo, no como un cambio ya hecho.
  • Pull requests de bifurcaciones. Como el flujo se activa con pull_request y no con pull_request_target, las PR de bifurcaciones no reciben secretos, que es el comportamiento deseado; la consecuencia práctica es que el despliegue de previsualización no funcionará para colaboradores externos, y es un compromiso aceptable.
  • Secreto de despliegue. Es un token de larga duración con permiso para publicar el sitio; si alguna vez se sospecha de una fuga, hay que regenerarlo en Azure y actualizarlo en GitHub.
  • Revisión de cambios. En un repositorio de un solo mantenedor no hay segundo revisor, pero un archivo CODEOWNERS que incluya .github/workflows sigue siendo útil en cuanto se sumen colaboradores.

Lista de verificación

Para llevarte algo accionable, esta es la lista condensada de controles en orden aproximado de rentabilidad (poco esfuerzo, mucho efecto, primero):

  1. Declarar permissions en cada workflow, empezando por {} o contents: read, y ampliar por trabajo.
  2. Poner el valor por defecto del GITHUB_TOKEN en solo lectura en los ajustes del repositorio u organización.
  3. No insertar nunca valores controlables por terceros con ${{ }} dentro de run:; pasarlos por variables de entorno.
  4. Evitar pull_request_target; si es imprescindible, no hacer checkout del código de la PR ni ejecutar nada procedente de ella, y usar persist-credentials: false.
  5. Fijar las acciones de terceros por el SHA completo de un commit, comprobando que procede del repositorio original, y mantenerlas actualizadas con Dependabot.
  6. Activar, donde esté disponible, la política que exige SHA y bloquear acciones y versiones concretas con el prefijo !.
  7. Preferir OIDC con credenciales de corta duración a los secretos de larga vida para desplegar en la nube, con condiciones de confianza estrechas.
  8. Usar secretos de entorno con aprobación de revisores para los despliegues sensibles.
  9. Añadir .github/workflows a CODEOWNERS.
  10. No usar ejecutores autoalojados en repositorios públicos; si se usan, que sean efímeros y estén aislados por grupos.
  11. Analizar los workflows con CodeQL y medir las prácticas con OpenSSF Scorecards.
  12. Tener un plan de respuesta: saber cómo rotar cada secreto y dónde mirar los registros.

Errores y malentendidos frecuentes

"Mis secretos están cifrados, así que no hay riesgo"

Los secretos se almacenan cifrados, pero en tiempo de ejecución se entregan en claro al proceso que los necesita. Una acción comprometida o una inyección de comandos puede leerlos y enviarlos fuera. El cifrado en reposo no protege de código malicioso que se ejecuta dentro del flujo.

"El enmascarado de los registros me protege"

El enmascarado oculta los valores conocidos en la salida, pero no impide que se exfiltren por otro canal, y no cubre valores derivados o codificados que no se hayan registrado. Es una red de seguridad, no un control de acceso.

"Mi repositorio es privado, no hace falta endurecer los workflows"

Un repositorio privado reduce la exposición a contribuyentes externos, pero no elimina el riesgo de las acciones de terceros ni el de colaboradores comprometidos. Y los repositorios privados pueden acabar siendo públicos o compartir ejecutores con otros.

"Fijar por SHA me hace inmune"

Protege contra el cambio de una etiqueta, pero no contra una acción maliciosa desde su primera versión, ni contra un SHA tomado de una bifurcación en lugar del repositorio original. Y si no se actualiza, se acumulan vulnerabilidades conocidas sin parche. Hay que combinarlo con revisión de código y con actualizaciones controladas.

"Con una etiqueta de aprobación estoy a salvo"

Como vimos, la condición de carrera entre la aprobación y la ejecución permite que el código cambie después de revisarlo. Solo se acepta como medida temporal.

"Los permisos por defecto son los correctos"

No hay que suponerlo: dependen de la configuración del repositorio u organización y pueden ser más amplios de lo necesario. Declarar permissions en el propio workflow hace explícita la intención y no depende del valor por defecto.

Preguntas frecuentes

¿Qué hago si sospecho que un secreto se ha filtrado?

Sigue la indicación de la documentación: elimina el registro donde apareció y rota el secreto, es decir, genera uno nuevo en el sistema de origen y retira el antiguo. Después revisa los registros de ejecuciones recientes en busca de actividad inesperada y, si el secreto daba acceso a un servicio, revisa también los accesos en ese servicio.

¿Es seguro usar acciones de la organización oficial de GitHub?

Las acciones mantenidas por GitHub (como actions/checkout) tienen menos riesgo que las de autores desconocidos, pero la documentación recomienda el mismo criterio de fijado y revisión para cualquier acción de terceros. Que sean oficiales reduce la probabilidad de compromiso; no la elimina.

¿Por qué no basta con revisar el código de la acción una vez?

Porque el código que se ejecuta es el de la versión que resuelve la referencia en cada ejecución. Si usas una etiqueta móvil, la versión puede cambiar sin que lo sepas. Fijar por SHA hace que lo revisado sea lo ejecutado; con un lockfile, GitHub lo verifica por ti.

¿Qué diferencia hay entre un secreto de repositorio y uno de entorno?

El de repositorio está disponible para cualquier trabajo del repositorio que lo solicite. El de entorno solo está disponible para los trabajos que despliegan en ese entorno, que puede exigir aprobaciones manuales antes de dar acceso a los secretos. Para valores sensibles, el de entorno ofrece un control adicional.

¿Puedo usar OIDC con proveedores distintos de Azure?

La documentación de GitHub describe OIDC de forma genérica, como un mecanismo para establecer una confianza entre GitHub y un proveedor de nube. La configuración concreta depende del proveedor; en este artículo solo hemos verificado el caso de Azure con su documentación oficial.

¿Los lockfiles sustituyen ya al fijado por SHA?

La documentación de GitHub dice que, para los repositorios que los adopten, sí lo sustituyen. Pero también indica que están en vista previa pública y sujetos a cambios. Hasta que sean estables, fijar por SHA con actualizaciones controladas sigue siendo la opción de base más segura y más conocida.

¿Qué es exactamente persist-credentials: false?

Es una opción de actions/checkout que evita que el token de autenticación se guarde en la configuración local de Git del ejecutor. El laboratorio de seguridad de GitHub la recomienda porque, por defecto, el checkout persiste las credenciales en disco, donde un paso posterior (o código malicioso) podría leerlas.

¿Cada cuánto debo revisar mis workflows?

No hay una cifra oficial, pero es razonable revisar los permisos, las referencias a acciones y los secretos cada vez que cambie el equipo o la infraestructura, y automatizar lo posible: Dependabot para actualizar versiones, análisis de código para detectar patrones de inyección y Scorecards para medir la postura general.

Conclusión

La seguridad de un pipeline de GitHub Actions no se resuelve con una única configuración, sino con una disciplina coherente: dar a cada pieza solo los permisos que necesita, no mezclar nunca datos de terceros con código ejecutable, no ejecutar código ajeno en contextos con privilegios y no depender de referencias móviles para el código que se ejecuta en tu nombre. Cada una de esas reglas tiene detrás un tipo concreto de ataque documentado: la inyección de scripts, la pwn request, el compromiso de una acción popular como el de tj-actions/changed-files.

La buena noticia es que los controles son baratos comparados con el daño que evitan. Declarar permissions, pasar los valores externos por variables de entorno, fijar las acciones por SHA y reemplazar los secretos de larga vida por OIDC son cambios pequeños en el archivo YAML que reducen de forma radical la superficie de ataque. Y la plataforma avanza en la dirección correcta, con políticas que obligan al fijado y con lockfiles que, cuando maduren, harán verificable lo que hoy se resuelve con disciplina.

Te sugerimos empezar por tus propios workflows con la lista de verificación de este artículo: bastan una hora y un editor de texto para encontrar las primeras mejoras. Si despliegas en la nube, completa el trabajo con una identidad federada y revisa los caminos por los que un secreto podría llegar a un registro. Y si quieres ver cómo se mueven los datos dentro de un flujo antes de endurecerlo, el artículo sobre la caché de GitHub Actions explica cómo se construyen y se reutilizan sus claves.
