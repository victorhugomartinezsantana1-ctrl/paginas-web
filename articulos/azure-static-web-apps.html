Investigación Profunda: Azure Static Web Apps

Arquitectura, pipelines CI/CD automatizados, entornos de PRs y configuración avanzada de enrutamiento.

por Victor Martinez 2026-10-20 ⏱ 15 min de lectura

1. Arquitectura y Fundamentos

Azure Static Web Apps (ASWA) no es un simple servidor de archivos. Es un servicio globalmente distribuido diseñado para aplicaciones de una sola página (SPAs como React, Angular, Vue), generadores de sitios estáticos (Gatsby, Hugo, Astro) y aplicaciones Blazor. Distribuye los archivos estáticos globalmente desde la red de borde de Azure (CDN), garantizando baja latencia desde cualquier parte del mundo.

Componentes Integrados:

  • Hospedaje Estático: Archivos HTML/CSS/JS distribuidos en la CDN.
  • APIs Serverless: Integración nativa con Azure Functions (se despliegan desde la misma carpeta api/ del repositorio).
  • Autenticación y Autorización: Proveedores preconfigurados (como GitHub y Microsoft Entra ID) y personalizados, gestionados en el archivo de configuración.

2. Flujo CI/CD con GitHub Actions (Anatomía del YAML)

Al crear el recurso, ASWA inyecta un workflow en .github/workflows/. El motor de este pipeline usa la acción oficial Azure/static-web-apps-deploy con la tecnología Oryx por debajo, la cual autodetecta el framework y compila el código sin que debas especificar comandos de build manuales.

yaml 
name: Azure Static Web Apps CI/CD
on:
  push:
    branches: [ "main" ]
  pull_request:
    types: [opened, synchronize, reopened, closed]
    branches: [ "main" ]

jobs:
  build_and_deploy_job:
    if: github.event_name == 'push' || (github.event_name == 'pull_request' && github.event.action != 'closed')
    runs-on: ubuntu-latest
    name: Build and Deploy
    steps:
      - uses: actions/checkout@v7
        with:
          submodules: true
      - name: Build And Deploy
        id: builddeploy
        uses: Azure/static-web-apps-deploy@v1
        with:
          azure_static_web_apps_api_token: ${{ secrets.AZURE_STATIC_WEB_APPS_API_TOKEN }}
          repo_token: ${{ secrets.GITHUB_TOKEN }}
          action: "upload"
          app_location: "/" # Raíz de la app (ej. /client)
          api_location: "api" # Carpeta de Azure Functions
          output_location: "dist" # Directorio de compilación (ej. build, dist)

  close_pull_request_job:
    if: github.event_name == 'pull_request' && github.event.action == 'closed'
    runs-on: ubuntu-latest
    name: Close Pull Request Job
    steps:
      - name: Close Pull Request
        id: closepullrequest
        uses: Azure/static-web-apps-deploy@v1
        with:
          azure_static_web_apps_api_token: ${{ secrets.AZURE_STATIC_WEB_APPS_API_TOKEN }}
          action: "close"
Staging Environments (Entornos de PR): El bloque pull_request en el YAML permite que Azure despliegue automáticamente una copia completa de la app en una URL temporal generada aleatoriamente (ej. gray-sand-0b1a.azurestaticapps.net) cada vez que abres un PR. Al cerrar el PR (merged o no), el job close_pull_request_job destruye el entorno para no generar costos extras. El plan Free admite hasta 3 entornos de ensayo a la vez.

3. Configuración Avanzada: staticwebapp.config.json

Para controlar el servidor, no puedes usar .htaccess o nginx.conf. En su lugar, ubicas un archivo staticwebapp.config.json en el directorio raíz de la app (junto a tu package.json). Permite configurar headers, rutas, autenticación y fallbacks.

json 
{
  "navigationFallback": {
    "rewrite": "/index.html",
    "exclude": ["/images/*.{png,jpg,gif}", "/css/*"]
  },
  "globalHeaders": {
    "Content-Security-Policy": "default-src https: 'unsafe-eval' 'unsafe-inline'; object-src 'none'"
  },
  "routes": [
    {
      "route": "/login",
      "rewrite": "/.auth/login/github"
    },
    {
      "route": "/admin/*",
      "allowedRoles": ["administrator"]
    }
  ]
}

El nodo navigationFallback es crítico para las SPAs (React/Vue/Angular), ya que redirige cualquier solicitud de ruta (ej. /productos/123) al index.html para que el enrutador del lado del cliente gestione la vista, evitando el clásico error 404 de servidor estático.

Las cabeceras de globalHeaders se aplican a cada respuesta. Ten cuidado con la Content-Security-Policy: una política demasiado restrictiva puede bloquear scripts de terceros, como los de Google AdSense o los de analítica. Pruébala siempre con la consola del navegador abierta.
