Investigación Exhaustiva: Kubernetes bajo el capó

Profundidad técnica en la arquitectura del Control Plane, Algoritmo Raft, CNI con eBPF y seguridad en K8s.

por Victor Martinez 2026-10-27 ⏱ 30 min de lectura

1. Introducción a la Orquestación a Gran Escala

Cuando el paradigma de Docker Multi-stage y Distroless nos permite tener imágenes de apenas unos pocos MB, el problema ya no es cómo compilar la aplicación, sino cómo gestionar cientos de contenedores operando simultáneamente. Si un contenedor muere, ¿quién lo reinicia? Si el tráfico se multiplica por diez, ¿cómo se escala horizontalmente? Si un servidor físico (nodo) se quema, ¿cómo se redistribuyen las cargas de trabajo sin pérdida de disponibilidad? Kubernetes (K8s) nace en Google (basado en su sistema interno Borg) para resolver estas interrogantes matemáticas y arquitectónicas mediante un bucle de control declarativo constante.

2. Anatomía del Control Plane (El Cerebro)

El "Control Plane" no ejecuta tu código de aplicación; toma decisiones globales sobre el clúster (planificación), detecta y responde a eventos del clúster (iniciar nuevos pods) y mantiene el estado deseado.

2.1 kube-apiserver

Es el componente frontal del panel de control. Todo componente interno o usuario externo (a través de kubectl) interactúa exclusivamente con el API Server. Funciona de manera stateless y escala horizontalmente. Actúa como un proxy de validación: recibe un archivo YAML, verifica la autenticación y autorización (RBAC), valida la sintaxis y luego muta el estado en la base de datos.

2.2 etcd: El Algoritmo Raft y la Consistencia Fuerte

Es un almacén clave-valor distribuido, consistente y altamente disponible. Kubernetes es stateless en todo su control plane, excepto en etcd. Aquí se guarda absolutamente todo: desde los Secrets hasta el estado actual de los Pods. Utiliza el algoritmo de consenso Raft, el cual requiere que la mayoría de los nodos (quórum) estén de acuerdo en una actualización antes de considerarla confirmada. Matemáticamente, para tolerar F fallos, necesitas 2F + 1 nodos de etcd. Por ello, los clústeres de producción siempre despliegan 3, 5 o 7 réplicas de etcd.

2.3 kube-scheduler

Observa los nuevos Pods creados que aún no tienen un Nodo asignado y selecciona uno para que se ejecuten. Su algoritmo consta de dos fases: Filtering (filtra nodos que no cumplen los requerimientos de hardware, memoria o afinidad) y Scoring (clasifica los nodos restantes para encontrar el más óptimo). Utiliza heurísticas para evitar concentrar todos los pods de un servicio en la misma máquina física, mitigando puntos únicos de fallo (SPOF).

2.4 kube-controller-manager

Es una colección de bucles de control (control loops) no bloqueantes que vigilan el estado compartido del clúster a través del apiserver y realizan cambios intentando mover el estado actual hacia el estado deseado. Incluye el Node Controller (reacciona cuando un nodo cae), el ReplicaSet Controller (garantiza que siempre haya X cantidad de pods corriendo) y el EndpointSlice Controller (mantiene actualizadas las reglas de red al cambiar las IPs de los pods).

3. Componentes del Nodo (Worker)

Los nodos son las máquinas de trabajo puro, donde tu código C++, Python o contenedores Nginx realmente consumen ciclos de CPU y RAM.

3.1 kubelet

Es un agente de node-level que corre en cada máquina física o virtual. Se asegura de que los contenedores estén corriendo y sanos. El kubelet lee los PodSpecs (descripciones de pods en YAML) proporcionados principalmente por el kube-apiserver y le ordena al Container Runtime que inicie o detenga los contenedores según corresponda. Implementa "Liveness" y "Readiness" probes, reiniciando contenedores si tus aplicaciones devuelven un error HTTP 500 constante.

3.2 kube-proxy e IPVS

Mantiene las reglas de red en los nodos. Estas reglas permiten la comunicación de red a los Pods desde el interior o el exterior del clúster. Históricamente usaba iptables de Linux, que es lineal (O(n)) al buscar reglas. En clústeres masivos con decenas de miles de servicios, la evaluación de iptables saturaba la CPU. La evolución moderna es usar IPVS (IP Virtual Server) o directamente eBPF (Extended Berkeley Packet Filter), que utilizan tablas hash (O(1)), permitiendo un ruteo de red casi instantáneo en el nivel del kernel de Linux. Además, desde Kubernetes 1.33 el modo nftables es estable y ofrece otra alternativa más eficiente que iptables.

4. Infraestructura de Red Avanzada (CNI y eBPF)

Kubernetes exige que: todos los pods puedan comunicarse con todos los demás pods sin NAT; todos los nodos puedan comunicarse con todos los pods sin NAT; y la IP que un pod ve de sí mismo sea la misma que los demás ven. Para cumplir estas leyes topológicas, usa CNI (Container Network Interface).

Soluciones como Cilium están revolucionando este espacio. Utilizan programas eBPF que se inyectan dinámicamente en el Kernel de Linux para interceptar paquetes de red en el momento preciso en que la tarjeta de red (NIC) los recibe (XDP - eXpress Data Path). Esto permite cifrar el tráfico entre pods con WireGuard, aplicar políticas de firewall en microsegundos y monitorear telemetría sin modificar el código de la aplicación, esquivando completamente la pila TCP/IP tradicional de Linux cuando no es necesaria.

5. Patrones de Diseño Declarativo (Manifiestos)

En lugar de ejecutar docker run (programación imperativa), en Kubernetes declaramos el objetivo en YAML. El control plane se encarga de la divergencia.

yaml 
apiVersion: apps/v1
kind: Deployment
metadata:
  name: microservicio-ia
  labels:
    app: backend-python
spec:
  replicas: 5 # Escalado horizontal
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1       # Nunca habrá más de 6 pods en actualización
      maxUnavailable: 0 # Nunca habrá menos de 5 pods disponibles
  selector:
    matchLabels:
      app: backend-python
  template:
    metadata:
      labels:
        app: backend-python
    spec:
      containers:
      - name: llm-worker
        image: tu-registry.com/llm-worker:v2.1.0 # Imagen distroless
        resources:
          requests:
            memory: "1024Mi"
            cpu: "500m" # Medio núcleo garantizado
          limits:
            memory: "2048Mi" # Si lo supera, el contenedor se termina (OOMKilled)
            cpu: "1000m" # Techo de CPU: al superarlo, el contenedor se ralentiza (throttling)
        livenessProbe:
          httpGet:
            path: /healthz
            port: 8080
          initialDelaySeconds: 15
          periodSeconds: 20
        readinessProbe:
          httpGet:
            path: /ready
            port: 8080
          initialDelaySeconds: 5
          periodSeconds: 10
Zero-Downtime Deployments (RollingUpdate): El manifiesto superior demuestra una técnica vital. Cuando cambias la etiqueta de la imagen de v2.0.0 a v2.1.0, Kubernetes no apaga todos tus servidores. Crea un nuevo Pod con la v2.1.0, espera a que pase el readinessProbe confirmando que está listo para recibir tráfico, y solo entonces destruye un Pod viejo de la v2.0.0. Repite esto hasta que todos los Pods son nuevos. Los usuarios finales jamás notan la caída del servicio.

6. Persistencia y Almacenamiento Dinámico (CSI)

Los contenedores son efímeros. Si un contenedor de base de datos PostgreSQL se reinicia, los datos almacenados en su sistema de archivos interno se pierden para siempre. Kubernetes resuelve esto abstrayendo el almacenamiento físico del software mediante PersistentVolumes (PV) y PersistentVolumeClaims (PVC) a través del Container Storage Interface (CSI).

En entornos cloud como Azure (AKS), cuando un desarrollador crea un PVC pidiendo "100 GiB de disco rápido", el CSI driver captura esta petición, interactúa vía API de Azure de forma transparente y provisiona físicamente un Azure Premium SSD, lo adjunta a la máquina virtual del Nodo correspondiente, lo formatea en Ext4, y lo monta en la ruta /var/lib/postgresql/data dentro del contenedor.

7. Seguridad y Aislamiento Multitenant

La seguridad en K8s sigue el modelo de Defensa en Profundidad (Defense in Depth).

  • RBAC (Role-Based Access Control): Limita estrictamente qué usuario o ServiceAccount puede realizar verbos (get, list, watch, create, delete) sobre qué recursos (pods, secrets) en qué Namespaces.
  • Network Policies: Por defecto, un clúster K8s es una red plana donde todo se comunica con todo. Las políticas de red son un firewall interno que aísla los microservicios. Ejemplo: "Solo el Pod 'Frontend' en el Namespace 'Producción' puede conectarse al Pod 'BaseDatos' en el puerto 5432". Para que se apliquen, el CNI debe implementarlas (Cilium y Calico lo hacen).
  • Seccomp y AppArmor: Limitan las llamadas al sistema (syscalls) que los procesos en C o Python pueden hacer hacia el kernel subyacente, impidiendo escaladas de privilegios incluso si un atacante explota una vulnerabilidad en el contenedor.

8. Conclusión: El Ecosistema Cloud-Native

Kubernetes no es solo un orquestador, es un sistema para construir sistemas distribuidos. Con la incorporación de CRDs (Custom Resource Definitions) y el patrón de Operadores (código que emula a un administrador humano interactuando con las APIs de K8s), el ecosistema se ha expandido para gestionar desde bases de datos complejas hasta la automatización de certificados SSL/TLS con Cert-Manager y la implementación de redes de mallas de servicios (Service Mesh) como Istio o Linkerd.
