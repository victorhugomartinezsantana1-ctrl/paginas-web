Investigación Exhaustiva: Rust vs C++ en Sistemas Embebidos y ESP32

Análisis profundo sobre manipulación de hardware a bajo nivel, seguridad de memoria, concurrencia RTOS y Asíncrona (Embassy).

por Victor Martinez 2026-10-27 ⏱ 5 min de lectura

1. El Paradigma de la Programación de Sistemas en Tiempo Real

Históricamente, el desarrollo embebido para microcontroladores (como el ESP32, STM32 o arquitecturas ARM Cortex-M) ha estado dominado hegemónicamente por C y C++. Estos lenguajes ofrecen abstracciones de "Zero-Cost" y manipulación directa de registros de hardware (a través de punteros volátiles y memoria no administrada), requisitos críticos para la modulación PWM, I2C, SPI o procesamiento de señales digitales (DSP). Sin embargo, esta libertad extrema conlleva un precio letal: la seguridad de la memoria.

2. Los Riesgos de C++: Punteros Colgantes y Fugas de Memoria

En la programación en C++, el programador es completamente responsable del ciclo de vida de la memoria en el Heap (montículo). Aunque herramientas modernas (C++11/14/17) introdujeron los Smart Pointers (std::unique_ptr, std::shared_ptr) y semánticas de movimiento, los errores de Use-After-Free (usar memoria ya liberada), Dangling Pointers (punteros colgantes) y Data Races (condiciones de carrera en multihilo) siguen detrás de aproximadamente el 70% de las vulnerabilidades de seguridad graves corregidas por Microsoft y por el proyecto Chromium de Google, según sus propios análisis.

En el contexto de la mecatrónica, un fallo de segmentación (segfault) por un acceso fuera de los límites de un arreglo en el núcleo de control de un sistema PID de estabilización o en el control de aceleración del motor de un vehículo eléctrico, no solo crashea el programa, sino que puede causar destrucción física de hardware o lesiones.

3. La Revolución de Rust: Propiedad y Préstamo (Ownership & Borrowing)

Rust es un lenguaje compilado multiparadigma (su compilador usa LLVM como backend, igual que Clang) que promete el mismo rendimiento nativo, pero garantiza la seguridad de memoria y seguridad en hilos en tiempo de compilación sin utilizar un Recolector de Basura (Garbage Collector). Lo logra mediante un conjunto de reglas estrictas verificadas por el Borrow Checker.

3.1 Las Reglas de Propiedad (Ownership)

  1. Cada valor en Rust tiene una variable que se llama su propietario (owner).
  2. Solo puede haber un propietario a la vez.
  3. Cuando el propietario sale del ámbito (scope), el valor se descarta automáticamente de la memoria (Drop).

A diferencia de C++, donde debes escribir delete obj;, en Rust el compilador inserta automáticamente la instrucción de limpieza en el punto exacto donde la variable ya no se utiliza. Las fugas de memoria son mucho más difíciles de provocar por accidente (aunque con ciclos de Rc o con mem::forget siguen siendo posibles).

3.2 Préstamos (Borrowing) y Mutabilidad Exclusiva

Rust prohíbe explícitamente los alias mutables. En un momento dado, puedes tener:

  • Cualquier cantidad de referencias inmutables (&T) a un dato (lectura concurrente segura).
  • O exactamente UNA referencia mutable (&mut T) a ese dato.
Garantía Data-Race Free: Debido a la regla de mutabilidad exclusiva, en Rust seguro (sin bloques unsafe) el compilador impide que dos hilos escriban en la misma región de memoria a la vez. Si detecta ese riesgo, el programa simplemente no compila.

4. Rust en el Metal Desnudo (Bare-Metal y ESP32)

Para programar el ESP32 en C++, generalmente usamos el entorno Arduino (muy limitado para tareas avanzadas) o el framework oficial de Espressif: ESP-IDF basado en FreeRTOS. Rust ofrece un soporte oficial y en constante evolución a través de esp-rs.

En Rust, programar para microcontroladores se divide en dos enfoques:

  • no_std (Bare Metal): Rust sin la biblioteca estándar (sin acceso a asignadores de memoria dinámica por defecto ni hilos del SO). Interactúa directamente con el hardware usando un HAL (Hardware Abstraction Layer). Extremadamente eficiente, código minúsculo.
  • std (Con sistema operativo): Rust con acceso completo a FreeRTOS, hilos, redes, usando envoltorios sobre ESP-IDF.

5. Comparación Práctica: Control PWM Multihilo

Veamos cómo varía la filosofía al controlar la aceleración de un motor y enviar telemetría en ambos lenguajes.

5.1 El Enfoque C++ con FreeRTOS (ESP-IDF)

cpp 
#include "freertos/FreeRTOS.h"
#include "freertos/task.h"
#include "freertos/semphr.h"
#include "driver/ledc.h"

// Variable global compartida (Peligro de Data Race sin Mutex)
volatile int motor_speed = 0; 
SemaphoreHandle_t speed_mutex;

void control_motor_task(void *pvParameter) {
    while(1) {
        if(xSemaphoreTake(speed_mutex, portMAX_DELAY)) {
            // Actualizar señal PWM en hardware
            ledc_set_duty(LEDC_LOW_SPEED_MODE, LEDC_CHANNEL_0, motor_speed);
            ledc_update_duty(LEDC_LOW_SPEED_MODE, LEDC_CHANNEL_0);
            xSemaphoreGive(speed_mutex);
        }
        vTaskDelay(pdMS_TO_TICKS(10)); // Context switch
    }
}

void telemetria_task(void *pvParameter) {
    while(1) {
        if(xSemaphoreTake(speed_mutex, portMAX_DELAY)) {
            printf("Velocidad Actual: %d\n", motor_speed);
            xSemaphoreGive(speed_mutex);
        }
        vTaskDelay(pdMS_TO_TICKS(500));
    }
}

extern "C" void app_main(void) {
    speed_mutex = xSemaphoreCreateMutex();
    xTaskCreate(control_motor_task, "motor", 2048, NULL, 5, NULL);
    xTaskCreate(telemetria_task, "telemetria", 2048, NULL, 1, NULL);
}

En C++, si olvidas usar xSemaphoreTake o devuelves prematuramente (por un return o una excepción) sin llamar a xSemaphoreGive, generas un Deadlock instantáneo o corrupción de datos. El compilador no te advierte. En C++ moderno puedes mitigarlo con RAII (por ejemplo std::lock_guard), pero sigue siendo una disciplina del programador y no una garantía del compilador.

5.2 El Enfoque Rust (Async/Await en Hardware usando Embassy)

Rust introduce Embassy, un framework asíncrono para sistemas embebidos. En lugar de pesadas tareas (Tasks) de FreeRTOS que consumen kilobytes de RAM para la pila de cada hilo y requieren cambios de contexto del kernel (Context Switches), Rust usa Futures compiladas a máquinas de estados minúsculas. Es cooperativo y mucho más ligero.

rust 
#![no_std]
#![no_main]

use embassy_executor::Spawner;
use embassy_time::{Duration, Timer};
use esp_hal::{
    clock::ClockControl, peripherals::Peripherals, 
    timer::TimerGroup, ledc::{Ledc, timer::TimerSel, channel}, 
    prelude::*
};
use core::sync::atomic::{AtomicU32, Ordering};

// Variable atómica inyectada, segura para hilos en hardware por defecto.
static MOTOR_SPEED: AtomicU32 = AtomicU32::new(0);

#[embassy_executor::task]
async fn control_motor_task(mut pwm_channel: channel::Channel<'static, esp_hal::peripherals::LEDC>) {
    loop {
        // Lectura atómica, sin locks pesados.
        let speed = MOTOR_SPEED.load(Ordering::Relaxed);
        pwm_channel.set_duty(speed).unwrap();
        // Yield asíncrono (cede control sin bloquear CPU)
        Timer::after(Duration::from_millis(10)).await;
    }
}

#[embassy_executor::task]
async fn telemetria_task() {
    loop {
        let speed = MOTOR_SPEED.load(Ordering::Relaxed);
        esp_println::println!("Velocidad Actual: {}", speed);
        Timer::after(Duration::from_millis(500)).await;
    }
}

#[esp_hal_embassy::main]
async fn main(spawner: Spawner) {
    let peripherals = Peripherals::take();
    // [...] Inicialización de reloj y PWM (omitiendo boilerplate por brevedad)
    
    // Generar concurrencia asíncrona segura. No hay RTOS, no hay sobrecarga de kernel.
    spawner.spawn(control_motor_task(pwm_channel)).unwrap();
    spawner.spawn(telemetria_task()).unwrap();
}

Aquí, el compilador verifica implícitamente todo. El uso de AtomicU32 evita locks lentos, y si pasaras una referencia incorrecta, Rust simplemente abortaría la compilación.

Sobre este código: el ecosistema esp-hal evoluciona rápido y los nombres de módulos, macros y tipos cambian entre versiones; además, set_duty espera un porcentaje (0-100) y no el valor bruto de un u32. El fragmento ilustra la estructura de las tareas asíncronas, no es un proyecto listo para compilar. Parte siempre de los ejemplos oficiales de esp-rs para la versión que uses.

6. Sistema de Construcción (Build System): CMake vs Cargo

Otra inmensa barrera en C++ es la gestión de dependencias. Integrar una librería de procesamiento de señales en C++ suele implicar peleas titánicas con CMakeLists.txt, subprocesos de Git y problemas de linking estático/dinámico. Rust viene con Cargo, un gestor de paquetes y sistema de construcción unificado.

bash 
# Añadir una librería para cálculos de matrices en microcontroladores es tan simple como:
cargo add nalgebra --no-default-features

Cargo compilará automáticamente las dependencias respetando la arquitectura de destino (por ejemplo xtensa-esp32-none-elf para el ESP32 clásico o riscv32imc-unknown-none-elf para el ESP32-C3 en modo no_std; con std los destinos terminan en -espidf) sin requerir modificaciones profundas en los flags del compilador.

7. Conclusión: ¿Cuándo usar cuál?

La Realidad de la Migración: Si tu proyecto requiere interactuar fuertemente con código heredado masivo, integraciones opacas del fabricante (blobs de radio WiFi propietarios o HALs específicos) que solo existen en C++, migrar completamente a Rust puede ser doloroso o usar FFI (Foreign Function Interface) con wrappers unsafe.

Sin embargo, para proyectos nuevos desde cero (Greenfield projects), especialmente aquellos que involucran control robótico crítico, sistemas interconectados IoT seguros o despliegues espaciales, Rust es una opción muy sólida, emparejando la previsibilidad inquebrantable de los lenguajes de bajo nivel con la ergonomía moderna del software de alto nivel.
