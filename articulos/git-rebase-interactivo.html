Investigación Profunda: Git Rebase Interactivo y Rewriting History

Manipulación del DAG de commits, split, squash, fixup y control absoluto sobre el historial.

por Victor Martinez 2026-09-17 ⏱ 16 min de lectura

1. Rebase vs Merge: El Grafo Acíclico (DAG)

Git guarda los commits como un grafo. Cuando usas git merge, creas un "Commit de Fusión" que une dos ramas, preservando la línea de tiempo original de manera no lineal. git rebase reescribe el historial. Toma los commits de tu rama actual, los extrae temporalmente, mueve la base de tu rama al final de la rama objetivo (ej. main) y "reproduce" (reaplica) tus commits uno por uno encima, creando nuevos hashes (SHAs). El resultado es un historial 100% lineal y limpio.

2. Entrando al Modo Interactivo (-i)

git rebase -i HEAD~N (donde N es el número de commits hacia atrás desde la punta) te abre un mundo de reestructuración. Al ejecutarlo, Git detiene el tiempo y presenta un script (todo-list) en el editor. Los commits aparecen en orden cronológico (el más antiguo arriba y el más nuevo abajo, en el orden en que se van a aplicar), al revés que en git log.

Operaciones Quirúrgicas:

  • pick (p): Aplica el commit normalmente. Puedes reordenar estas líneas en el editor para cambiar el orden de los commits en la historia final.
  • edit (e): El poder de detener el tiempo. Git pausa el rebase justo después de aplicar este commit. Aquí puedes ejecutar comandos, o hacer git reset HEAD~1 para "deshacer" el commit dejando los archivos en el working tree, de modo que puedas crear dos commits separados de lo que antes era uno (Split de commit), y luego ejecutar git rebase --continue.
  • squash (s) vs fixup (f): Ambos unen el commit actual con el de la línea anterior (arriba). La diferencia es que squash te pide fusionar los mensajes de ambos commits, mientras que fixup descarta el mensaje del actual e integra su contenido de forma invisible al commit original. Ideal para cuando subiste un "wip" o corregiste un error tipográfico en el commit anterior.
  • exec (x): Automáticamente ejecuta un comando shell en cada paso del rebase. Ej: exec npm test (Se pone después de un pick). Si los tests fallan en ese punto de la historia, el rebase se pausa para que arregles el error (evitando commits rotos en el historial).

3. La Red de Seguridad: git reflog

¿Qué pasa si arruinas un rebase, eliminas un commit importante y haces un squash desastroso? No entres en pánico. Git nunca borra commits inmediatamente. Todo commit huérfano (cuyo apuntador fue movido por un rebase) se conserva en el reflog: por defecto Git guarda las entradas 90 días (30 días si ya no son alcanzables).

bash 
# Ver el historial de TODOS los movimientos del puntero HEAD
git reflog
# Localizar el SHA antes de iniciar el rebase (ej. HEAD@{4})
git reset --hard HEAD@{4}

# Atajo: justo después de un rebase, ORIG_HEAD apunta al estado anterior
git reset --hard ORIG_HEAD

Con un solo comando de reset, anulas el rebase completo y vuelves exactamente al estado inicial.

4. La Regla de Oro

Peligro: Nunca hagas rebase de una rama (branch) pública compartida que otros desarrolladores ya tengan en local. Si reescribes la historia de main y fuerzas la subida (git push -f), los Git locales de tus compañeros presentarán historias divergentes, y al hacer pull crearán merge commits duplicados que ensucian el historial y obligan a resolver conflictos innecesarios. Haz rebase SOLO en tus ramas de características (feature branches) locales antes de solicitar la fusión. Si tras un rebase de tu propia rama necesitas actualizarla en el remoto, usa git push --force-with-lease, que se niega a sobrescribir commits que no tengas en local.
