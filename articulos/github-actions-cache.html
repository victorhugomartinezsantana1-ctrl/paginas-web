Investigación Profunda: Caché en GitHub Actions

Optimización de CI/CD: claves con hash, restore keys, rutas por ecosistema y límites de caché.

por Victor Martinez 2026-10-14 ⏱ 12 min de lectura

1. ¿Por qué el Caché es Crítico en CI/CD?

En pipelines modernos, descargar cientos de megabytes desde NPM, Maven Central o PyPI en cada commit de cada Pull Request multiplica el tiempo de despliegue y quema los minutos gratuitos de GitHub Actions (facturados por minuto de cómputo). actions/cache mitiga esto creando un archivo comprimido (tarball) del directorio objetivo y guardándolo en el backend de GitHub asociado a una llave (key) específica.

2. Anatomía y Ciclo de Vida del actions/cache

La acción funciona en dos fases invisibles conectadas por la clave primaria key:

  1. Fase de Restauración (Post-checkout): Busca en GitHub si existe el tarball con la clave exacta. Si existe (Cache Hit), lo descarga y descomprime en el path indicado. Si no existe (Cache Miss), no hace nada.
  2. Fase de Guardado (Post-job): Al final del pipeline, si hubo un Cache Miss y el trabajo fue exitoso, comprime el directorio del path y lo sube con la clave especificada.

3. Estrategias de Hashing y Restore Keys

La clave primaria debe cambiar únicamente cuando las dependencias cambian. Por eso se usa hashFiles sobre el archivo de bloqueo (lockfile).

yaml 
- name: Cache Node modules
  uses: actions/cache@v6
  with:
    path: ~/.npm
    key: ${{ runner.os }}-node-${{ hashFiles('**/package-lock.json') }}
    restore-keys: |
      ${{ runner.os }}-node-

El poder de las restore-keys

Si cambias una sola dependencia, el hash del package-lock.json cambiará completamente provocando un Cache Miss. Aquí entran las restore-keys, que actúan como "fallbacks" de búsqueda por prefijo.

Si la clave principal Linux-node-abc123hash falla, GitHub busca la caché más reciente que empiece por Linux-node-. Descargará esa caché antigua, el npm ci tardará solo unos segundos en instalar la única dependencia nueva, y al final del job se guardará una nueva caché con el hash actualizado. Eficiencia máxima.

4. Ejemplos de Rutas Comunes por Ecosistema

  • Python (pip): path: ~/.cache/pip
  • Java (Maven): path: ~/.m2/repository
  • Java (Gradle): path: ~/.gradle/caches
  • Go (Módulos): path: ~/go/pkg/mod
  • Rust (Cargo): path: ~/.cargo/registry y target/

5. Límites y Políticas de Evicción

Importante: GitHub impone un límite de 10 GB de caché por repositorio. Si superas este límite, GitHub elimina automáticamente las cachés más antiguas o menos utilizadas (política LRU - Least Recently Used). Además, cualquier caché que no haya sido accedida en 7 días se borra permanentemente.
