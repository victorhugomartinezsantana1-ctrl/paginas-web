Investigación Exhaustiva: Terraform y la automatización Cloud con Azure

Transición desde ClickOps hacia Infraestructura como Código: Idempotencia, manejo de estados (TFState) y GitOps en PostgreSQL y ASWA.

por Victor Martinez 2026-10-27 ⏱ 25 min de lectura

1. El Desafío de la Infraestructura Manual

En nuestro artículo sobre Azure Static Web Apps, vimos la facilidad de hacer "click" en el portal de Azure para desplegar un recurso. Pero en entornos de ingeniería profesionales, aprovisionar recursos mediante interfaces gráficas (ClickOps) se considera un grave antipatrón. Es lento, propenso a errores humanos, no escalable, imposible de auditar históricamente y no permite replicar un entorno idéntico de "Producción" para un ambiente de "Pruebas" sin días de trabajo manual. La solución a este caos operacional es la Infraestructura como Código (IaC).

2. Terraform: El Estándar de la Industria

Desarrollado por HashiCorp (en 2023 cambió su licencia a BSL y la comunidad creó OpenTofu como fork de código abierto), Terraform es una herramienta declarativa. Escribes archivos de configuración (.tf) utilizando HCL (HashiCorp Configuration Language) para describir cómo debería lucir la infraestructura de tu centro de datos (estado final deseado), y Terraform se encarga de determinar la secuencia exacta de llamadas a las APIs de Azure, AWS o Google Cloud para hacer realidad ese estado.

2.1 Idempotencia: El Pilar del Diseño

A diferencia de un script de bash o de Python que, si lo ejecutas dos veces seguidas, intentará crear una máquina virtual dos veces y fallará (o creará dos y duplicará tus costos), Terraform es idempotente. Al ejecutar terraform apply cincuenta veces sin cambiar el código, no hará absolutamente nada las últimas cuarenta y nueve, reconociendo que el estado en la nube ya coincide con tu código local.

3. Arquitectura del Proveedor (AzureRM Provider)

Terraform interactúa con Azure utilizando el proveedor azurerm, un binario plugin escrito en lenguaje Go que traduce tu código HCL en requests HTTPS JSON hacia el Azure Resource Manager (ARM).

hcl 
# 1. Bloque de configuración base
terraform {
  required_providers {
    azurerm = {
      source  = "hashicorp/azurerm"
      version = "~> 4.0" # Limita versiones para evitar breaking changes
    }
    random = {
      source  = "hashicorp/random"
      version = "~> 3.0"
    }
  }
}

# 2. Inicialización del Provider
provider "azurerm" {
  features {} # Requerido obligatoriamente, maneja comportamientos globales
  # En azurerm 4.x hay que indicar la suscripción: subscription_id aquí
  # o la variable de entorno ARM_SUBSCRIPTION_ID
}

# 3. Creación de un Grupo de Recursos
resource "azurerm_resource_group" "rg_principal" {
  name     = "devlog-produccion-rg"
  location = "eastus2"
}

4. Automatización Completa: Azure Static Web App y base de datos PostgreSQL

Elevemos la complejidad. En un solo archivo, vamos a desplegar tu página web estática, pero además vamos a aprovisionar un servidor de base de datos PostgreSQL seguro, vinculándolos en la misma región de manera automatizada. Esta operación manual en el portal tomaría unos 30 clics en docenas de pantallas distintas.

hcl 
# 4. Azure Static Web App (Infraestructura declarada)
resource "azurerm_static_web_app" "web_frontend" {
  name                = "devlog-sitio-web"
  resource_group_name = azurerm_resource_group.rg_principal.name
  location            = azurerm_resource_group.rg_principal.location
  sku_tier            = "Free"
  sku_size            = "Free"

  tags = {
    environment = "produccion"
    project     = "investigacion-iac"
  }
}

# 5. Generador aleatorio de contraseñas de alta entropía
resource "random_password" "db_password" {
  length           = 24
  special          = true
  override_special = "!#$%&*()-_=+[]{}<>:?"
}

# 6. Servidor PostgreSQL Flexible Server
resource "azurerm_postgresql_flexible_server" "db_backend" {
  name                   = "devlog-postgres-db"
  resource_group_name    = azurerm_resource_group.rg_principal.name
  location               = azurerm_resource_group.rg_principal.location
  version                = "16"
  administrator_login    = "dbadmin_devlog"
  administrator_password = random_password.db_password.result
  
  # Almacenamiento y Cómputo ajustable
  storage_mb           = 32768
  sku_name             = "B_Standard_B1ms" # Capa B (Burstable) ideal para pruebas
  zone                 = "1"
}

# 7. Regla de Firewall (permite el acceso desde servicios de Azure)
resource "azurerm_postgresql_flexible_server_firewall_rule" "allow_azure" {
  name             = "AllowAzureServices"
  server_id        = azurerm_postgresql_flexible_server.db_backend.id
  start_ip_address = "0.0.0.0"
  end_ip_address   = "0.0.0.0" # Valor especial: permite a cualquier servicio de Azure
}
Cuidado con la regla 0.0.0.0: no limita el acceso a tu Static Web App, sino que permite conexiones desde cualquier servicio de Azure, incluidos los de otros clientes. Sirve para pruebas; en producción usa una red virtual con Private Endpoint o restringe las IP de origen. Además, un sitio estático no se conecta a la base de datos por sí mismo: solo lo harían sus funciones de API.

5. State File (el Talón de Aquiles y el corazón de Terraform)

¿Cómo sabe Terraform que el recurso azurerm_static_web_app en tu código es exactamente el mismo que ya está corriendo en la nube? A través del archivo de estado terraform.tfstate. Es un documento JSON autogenerado que mapea los bloques de código locales con los IDs reales generados por Azure (ej. /subscriptions/5f2b.../resourceGroups/...).

Advertencia Crítica de Seguridad: El archivo .tfstate almacena los datos en TEXTO PLANO, incluyendo las contraseñas que generes en el código (como la del PostgreSQL en el paso anterior) o los tokens de conexión. JAMÁS debes subir este archivo a GitHub (debe estar excluido en el .gitignore). En producción, este archivo se configura para almacenarse de forma remota y encriptada en un Azure Blob Storage utilizando la funcionalidad de Remote Backend de Terraform, junto con mecanismos de bloqueo (Locking) para que dos ingenieros no ejecuten apply simultáneamente y corrompan la infraestructura.

Como mínimo, excluye estos archivos en tu .gitignore:

.gitignore 
*.tfstate
*.tfstate.*
.terraform/
*.tfvars

6. El Ciclo de Vida en Terminal (Workflow)

  • terraform init: Descarga el plugin azurerm y configura el backend.
  • terraform plan: Analiza tu código, lee la nube de Azure y construye un gráfico de dependencias (DAG). Imprime en pantalla un resumen de "Plan: 5 to add, 0 to change, 0 to destroy" antes de tocar nada real.
  • terraform apply: Ejecuta el plan tras una confirmación.
  • terraform destroy: Aniquila la infraestructura completa referenciada en el estado. Esencial para entornos efímeros (crear todo el viernes para pruebas y destruirlo a los pocos minutos para no pagar en el fin de semana).

7. Integración CI/CD (GitHub Actions + Terraform)

Para unir las piezas del rompecabezas, el paso final evolutivo es que los humanos no tengan permisos para ejecutar terraform apply desde sus portátiles. Se otorgan los permisos de despliegue a una identidad de Azure (un Service Principal con credenciales federadas OIDC, sin secretos de larga duración) vinculada a GitHub. Al crear un Pull Request en GitHub con un cambio en el archivo .tf, un GitHub Action ejecuta terraform plan y lo comenta automáticamente en el PR. Cuando el equipo aprueba el cambio y hace "Merge", otro Action ejecuta terraform apply. La infraestructura se despliega sola, auditada, sin interacciones manuales y sincronizada eternamente con el repositorio de código, instaurando el verdadero concepto de GitOps.
