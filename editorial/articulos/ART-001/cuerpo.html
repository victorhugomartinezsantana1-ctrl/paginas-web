La mayoría de las personas usa Git como una caja negra con unos pocos comandos: add, commit, push, pull, y alguna vez rebase o reset cuando algo sale mal. Funciona, hasta que deja de funcionar. Un reset --hard que parece haber destruido una tarde de trabajo, un repositorio que de pronto ocupa varios gigabytes, una rama que "desapareció" tras un rebase, un mensaje críptico sobre detached HEAD: todos esos momentos se vuelven mucho menos aterradores cuando uno entiende qué hay realmente dentro de la carpeta .git.

La buena noticia es que el modelo interno de Git es sorprendentemente pequeño. No hay una base de datos oculta ni formatos exóticos: hay un almacén de objetos que se identifican por el hash de su contenido, un puñado de archivos de texto que apuntan a esos objetos (las referencias) y algunos mecanismos de mantenimiento que empaquetan y limpian lo que ya no hace falta. Todo lo que Git hace por encima, desde crear ramas hasta fusionarlas, se construye sobre esas piezas.

Este artículo recorre ese modelo de abajo arriba. No nos limitamos a describirlo: lo comprobamos con comandos que puedes ejecutar en tu equipo. Los resultados que verás en los bloques de código proceden de un laboratorio real ejecutado con Git 2.56.0 el 27 de octubre de 2026, con una identidad y unas fechas fijadas para que los hashes sean reproducibles. Cuando una cifra o un comportamiento proviene de la documentación oficial o del libro Pro Git, se indica con su fuente al final del texto. Si ya conoces el flujo de trabajo cotidiano, te sugerimos leer después nuestro artículo sobre rebase interactivo y reescritura del historial, que cobra mucho más sentido una vez que se sabe qué significa "reescribir" un commit.

Puntos clave
  • Git es, en su núcleo, un almacén clave-valor: la clave de cada objeto es el hash SHA-1 de su contenido más una cabecera con tipo y tamaño.
  • Existen cuatro tipos de objeto: blob (contenido de un archivo), tree (un directorio), commit (una instantánea con metadatos y padres) y tag (una etiqueta anotada).
  • Las ramas, las etiquetas ligeras y HEAD no son objetos: son archivos pequeños que contienen un hash o apuntan a otra referencia.
  • Los objetos nuevos se guardan sueltos y comprimidos con zlib; git gc los agrupa en packfiles donde las versiones parecidas se almacenan como deltas.
  • El reflog registra cada movimiento de HEAD en local; por defecto caduca a los 90 días (30 si la entrada ya no es alcanzable) y es lo que permite recuperar commits aparentemente perdidos.
  • Git está migrando de SHA-1 a SHA-256, pero la propia documentación presenta esa transición como un diseño en marcha y no como un cambio ya completado.

Un sistema de archivos direccionable por contenido

La definición más precisa de Git que ofrece Pro Git es que se trata de un sistema de archivos direccionable por contenido (content-addressable filesystem) con una interfaz de control de versiones por encima. Dicho sin jerga: es un almacén en el que guardas datos y recibes a cambio una clave que depende únicamente de esos datos. Si guardas el mismo contenido dos veces obtienes la misma clave y, por tanto, un solo objeto. Si cambias un solo byte obtienes otra clave completamente distinta.

Esa idea, aparentemente simple, tiene consecuencias enormes. La primera es la deduplicación automática: un archivo que no cambia entre cien commits se almacena una única vez, porque en los cien commits apunta al mismo objeto. La segunda es la integridad: como la clave es una función del contenido, Git puede detectar corrupción recalculando el hash y comparándolo con el nombre. La tercera, que veremos más adelante, es la inmutabilidad: un objeto nunca se modifica; si algo cambia, aparece un objeto nuevo con otro identificador.

Fontanería y porcelana

En la jerga de Git, los comandos de alto nivel que usamos a diario (add, commit, checkout, merge) forman la "porcelana", mientras que un conjunto de comandos de bajo nivel, pensados originalmente para construir herramientas por encima, constituyen la "fontanería" (plumbing). Los comandos de fontanería que usaremos en este artículo son hash-object, cat-file, update-index, write-tree, commit-tree, update-ref, symbolic-ref y verify-pack. No necesitas memorizarlos: sirven como lupa para observar qué hace la porcelana cuando ejecutas un git commit normal.

Tu primer objeto

Crea un repositorio vacío y guarda una cadena de texto directamente en el almacén de objetos. La opción -w pide que se escriba el objeto en la base de datos; sin ella, el comando solo calcula y muestra la clave.

git init demo
cd demo
echo 'hola mundo' | git hash-object --stdin
# 24db42bb7b999597a72801da70efd5876059bc0b

echo 'hola mundo' | git hash-object -w --stdin
# 24db42bb7b999597a72801da70efd5876059bc0b

git cat-file -t 24db42b   # blob
git cat-file -s 24db42b   # 11
git cat-file -p 24db42b   # hola mundo

Observa tres cosas. Primero, el hash es el mismo con y sin -w: la clave solo depende del contenido, no de si lo has guardado o no. Segundo, cat-file -t informa de que el objeto es de tipo blob. Tercero, el tamaño es 11 bytes, que son los diez caracteres de "hola mundo" más el salto de línea que añade echo. Si repites el experimento con echo -n, que omite ese salto de línea, obtendrás un hash distinto, porque el contenido es distinto. Esta sensibilidad a cada byte es exactamente lo que se espera de un sistema direccionable por contenido.

Cómo se calcula el identificador de un objeto

El hash de un objeto no se calcula solo sobre su contenido. Según Pro Git, Git antepone una cabecera formada por el tipo del objeto, un espacio, el tamaño en bytes expresado en decimal y un byte nulo (\0). El SHA-1 se calcula sobre la concatenación de esa cabecera y el contenido. Después, la misma cadena (cabecera más contenido) se comprime con zlib y se escribe en un archivo cuya ruta se deriva del hash: los dos primeros caracteres hexadecimales forman el nombre de un subdirectorio dentro de .git/objects y los treinta y ocho restantes, el nombre del archivo.

Podemos verificarlo sin Git, con unas líneas de Python. El programa reproduce el cálculo del hash y, de paso, descomprime el objeto real del disco para comprobar que su contenido coincide con la cadena que acabamos de construir.

import hashlib, zlib

contenido = b'hola mundo\n'
almacenado = b'blob %d\x00' % len(contenido) + contenido

print(hashlib.sha1(almacenado).hexdigest())
# 24db42bb7b999597a72801da70efd5876059bc0b  (idéntico al de git hash-object)

ruta = '.git/objects/24/db42bb7b999597a72801da70efd5876059bc0b'
print(zlib.decompress(open(ruta, 'rb').read()))
# b'blob 11\x00hola mundo\n'

El resultado confirma el mecanismo descrito por la documentación: el identificador es el SHA-1 de blob 11\0hola mundo\n y el archivo en disco contiene exactamente esos bytes comprimidos. No hay metadatos escondidos ni índices auxiliares: el nombre del archivo es el hash del propio contenido.

Por qué importa la cabecera. Gracias al prefijo con el tipo, un blob y un tree que tuvieran por casualidad los mismos bytes de contenido tendrían identificadores diferentes. La cabecera separa los "espacios de nombres" de los distintos tipos de objeto dentro del mismo almacén.

Los cuatro tipos de objeto

Con el mecanismo de almacenamiento claro, falta saber qué se guarda. Git utiliza cuatro tipos de objeto. Los tres primeros construyen una instantánea del proyecto; el cuarto sirve para marcar versiones.

Blob: el contenido de un archivo

Un blob (de binary large object) almacena los bytes de un archivo y nada más. Es importante recalcar lo que un blob no contiene: ni el nombre del archivo, ni su ruta, ni sus permisos, ni la fecha. Dos archivos con nombres distintos y el mismo contenido comparten el mismo blob. Renombrar un archivo sin tocar su contenido no crea ningún blob nuevo.

Tree: un directorio

El nombre, la ruta y los permisos viven en los objetos tree, que representan directorios. Un tree es una lista de entradas, y cada entrada indica un modo, un tipo, el hash del objeto referenciado y un nombre. Pro Git documenta los modos válidos para archivos: 100644 para un archivo normal, 100755 para un ejecutable y 120000 para un enlace simbólico, además de 040000 para un subdirectorio, que apunta a otro tree. Los árboles se anidan: el tree de la raíz apunta a blobs (archivos) y a otros trees (subdirectorios), y así sucesivamente.

Podemos construir un tree a mano. Primero añadimos al índice una entrada que apunta al blob que ya existe y después pedimos a Git que escriba el índice como tree:

git update-index --add --cacheinfo 100644 24db42bb7b999597a72801da70efd5876059bc0b hola.txt
git write-tree
# 10e30303e3aef2eed251953d04e58bb67d6c777a

git cat-file -p 10e30303e3aef2eed251953d04e58bb67d6c777a
# 100644 blob 24db42bb7b999597a72801da70efd5876059bc0b	hola.txt

Fíjate en que el archivo hola.txt nunca existió en el directorio de trabajo. Le hemos dicho a Git que el nombre hola.txt debe apuntar al blob con ese hash, y Git lo ha registrado. Esta es la prueba más clara de que el contenido y el nombre son cosas separadas.

Commit: una instantánea con historia

Un commit es un objeto que apunta al tree raíz del proyecto en un momento dado, a cero o más commits padre y a información de autoría. Su contenido es un texto legible: una línea tree con el hash del directorio raíz, una línea parent por cada commit padre, una línea author y otra committer (cada una con nombre, correo, marca de tiempo y zona horaria), una línea en blanco y el mensaje.

echo 'Primer commit' | git commit-tree 10e30303e3aef2eed251953d04e58bb67d6c777a
# fc720b7fb6da046161a1bea8a620832b6eab9c29

git cat-file -p fc720b7
# tree 10e30303e3aef2eed251953d04e58bb67d6c777a
# author Ada <ada@example.com> 1767268800 +0000
# committer Ada <ada@example.com> 1767268800 +0000
#
# Primer commit

git cat-file -s fc720b7   # 156

El primer commit no tiene línea parent, porque no hay historia previa. Todos los demás tendrán al menos una. Un detalle útil: el identificador de un commit depende de todo su contenido, incluido el hash del tree, los padres, el autor y la marca de tiempo. Por eso, para obtener hashes reproducibles en este laboratorio fijamos las fechas con las variables de entorno GIT_AUTHOR_DATE y GIT_COMMITTER_DATE. Sin esa precaución, ejecutar los mismos comandos un segundo más tarde produciría un hash diferente.

Tag: una etiqueta anotada

El cuarto tipo es el objeto tag, que usan las etiquetas anotadas. Lo veremos en la sección de referencias, porque su función es marcar un punto concreto de la historia y suele ir acompañado de un archivo en refs/tags.

Del contenido a la historia: por qué los commits son inmutables

Hemos visto que un commit contiene el hash de su tree y los hashes de sus padres. Consideremos las consecuencias. El identificador de un commit se calcula sobre su contenido, que incluye el identificador de su padre. Por tanto, si alguien modificase de algún modo un commit antiguo, su hash cambiaría, y como el hijo lo referencia por hash, el contenido del hijo también cambiaría, y por tanto su hash, y así hasta la punta de la rama. La historia de Git es, en términos técnicos, una cadena de hashes: cualquier alteración se propaga y es detectable.

Esto explica el comportamiento de comandos como rebase o commit --amend. Cuando "modificas" un commit, en realidad Git crea un commit nuevo con otro hash y mueve la rama para que lo apunte; el commit antiguo sigue existiendo, intacto, hasta que algún proceso de limpieza lo elimine. Es exactamente lo que describe Pro Git cuando explica que un rebase toma los commits de tu rama y los reaplica creando nuevos hashes. También explica por qué reescribir historia publicada es problemático: los compañeros que tengan los commits antiguos tienen, literalmente, objetos diferentes de los que ahora hay en el servidor.

Merge: commits con dos padres

La historia no es una línea, sino un grafo acíclico dirigido (DAG): cada commit apunta a sus padres y ningún camino puede volver sobre sí mismo. Un commit de fusión (merge) es un commit corriente que tiene dos o más líneas parent. En el laboratorio creamos una rama, añadimos un commit y la fusionamos con --no-ff para forzar un commit de fusión. El resultado en bruto:

git cat-file -p HEAD
# tree 033036e4414b4f7882f571c381b3cde88bc9f7f8
# parent 1a787065968d794b6a2e7e1aa3e959aec8d46726
# parent e12ca9e0b922e44d5d20a1192b64d6b13dc363cc
# author Ada <ada@example.com> ...

Los dos padres son, por orden, la punta de la rama en la que estábamos (main) y la punta de la rama fusionada. Esa distinción importa: la notación HEAD^1 y HEAD~1 designan el primer padre, mientras que HEAD^2 designa el segundo. Y también explica por qué revertir un merge exige indicar con -m qué padre se considera la línea principal.

Alcanzabilidad: qué commits "existen" para Git

Dicho de forma práctica, un commit está vivo mientras sea alcanzable desde alguna referencia (una rama, una etiqueta, HEAD) siguiendo la cadena de padres. Cuando ya no hay ninguna referencia que llegue hasta él, queda huérfano. Los commits huérfanos no desaparecen de inmediato: siguen en el almacén de objetos hasta que la limpieza los elimina, y mientras tanto el reflog suele ofrecer una forma de volver a llegar a ellos. Lo veremos en detalle más abajo.

El índice: la zona de preparación

Hasta ahora hemos usado update-index y write-tree sin explicar qué hay entre ambos. Ese intermediario es el índice (o staging area), un archivo binario en .git/index que describe el siguiente tree que se va a confirmar: para cada ruta, el modo, el hash del blob y algunos metadatos que permiten detectar rápidamente cambios en el directorio de trabajo.

Con esa pieza, el comportamiento de los dos comandos más comunes queda desmitificado. Según Pro Git, git add y git commit realizan internamente los mismos pasos que hemos ejecutado a mano: add guarda el contenido de los archivos como blobs y actualiza el índice; commit escribe el índice como una jerarquía de trees, crea un objeto commit que apunta al tree raíz y al commit actual como padre, y mueve la rama actual para que apunte al nuevo commit.

  1. Guardar los blobs. Por cada archivo añadido, Git calcula el hash y escribe el objeto, como hicimos con hash-object -w.
  2. Actualizar el índice. La ruta del archivo pasa a apuntar al nuevo blob, igual que con update-index --cacheinfo.
  3. Escribir los trees. Al hacer commit, el índice se convierte en objetos tree anidados (write-tree).
  4. Crear el commit. Se escribe un objeto commit con el tree raíz, el padre y los metadatos (commit-tree).
  5. Mover la referencia. La rama actual se actualiza para apuntar al commit nuevo (update-ref).

Dos efectos prácticos se deducen de esta secuencia. Primero, un archivo que añades con git add y luego modificas otra vez en disco tiene una versión en el índice y otra distinta en el directorio de trabajo; el commit solo recogerá la del índice. Segundo, git add ya ha escrito el blob en el almacén de objetos, así que, incluso si deshaces el add, ese contenido puede quedar en el almacén como objeto suelto hasta una futura limpieza. Es una de las razones por las que a veces git fsck descubre blobs "colgantes" sin ninguna historia asociada.

Referencias: ramas, etiquetas y HEAD

Los objetos son inmutables y se identifican por hashes largos, difíciles de recordar. Para trabajar de forma humana, Git añade una capa de nombres: las referencias. Una referencia es, simplemente, un archivo de texto bajo .git/refs cuyo contenido es un hash. Pro Git lo muestra con un experimento que puedes reproducir: crear una rama es escribir un hash en un archivo.

git update-ref refs/heads/main fc720b7fb6da046161a1bea8a620832b6eab9c29

cat .git/refs/heads/main
# fc720b7fb6da046161a1bea8a620832b6eab9c29

git log --oneline
# fc720b7 Primer commit

La documentación recomienda no editar esos archivos a mano y usar git update-ref, que además se encarga de registrar el movimiento en el reflog. Una rama es, por tanto, un puntero móvil: cuando haces un commit estando en ella, Git escribe el hash del nuevo commit en ese archivo. Crear una rama nueva no copia nada; solo crea otro archivo con un hash. Esta es la razón técnica de que las ramas de Git sean tan baratas.

Los espacios de nombres de las referencias

Las referencias se organizan por directorios, y ese directorio indica su significado:

  • refs/heads/: ramas locales.
  • refs/tags/: etiquetas.
  • refs/remotes/<remoto>/: copias de las ramas de los repositorios remotos, tal como estaban la última vez que te comunicaste con ellos.

Las referencias remotas merecen una nota. Según Pro Git, son prácticamente de solo lectura: puedes hacer checkout de una, pero Git nunca hace que HEAD apunte simbólicamente a ella, de modo que un commit nunca la actualiza. Actúan como marcadores de dónde estaban esas ramas la última vez que hablaste con el servidor. Se actualizan con fetch y push.

HEAD: la referencia simbólica

¿Cómo sabe Git en qué rama estás? A través de HEAD. Normalmente HEAD no contiene un hash, sino una referencia simbólica, es decir, el nombre de otra referencia:

cat .git/HEAD
# ref: refs/heads/main

git symbolic-ref HEAD
# refs/heads/main

Cuando haces un commit, Git resuelve HEAD para saber qué rama debe mover, y usa el commit al que apunta esa rama como padre del commit nuevo. Cambiar de rama con checkout o switch consiste, en esencia, en reescribir HEAD para que apunte simbólicamente a otra rama y actualizar el directorio de trabajo para que coincida con su tree.

Detached HEAD, sin misterio. En ocasiones HEAD contiene directamente un hash en lugar de un nombre de rama. Eso ocurre, por ejemplo, al hacer checkout de una etiqueta, de un commit concreto o de una rama remota. En ese estado, los commits que crees no avanzan ninguna rama: si cambias de rama sin crear antes una nueva, esos commits solo serán alcanzables a través del reflog. La solución es tan sencilla como crear una rama en el commit actual antes de marcharte.

Etiquetas ligeras y anotadas

Existen dos tipos de etiquetas, y la diferencia es puramente estructural. Una etiqueta ligera es una referencia en refs/tags que apunta directamente a un commit y nunca se mueve. Una etiqueta anotada es un objeto tag independiente, que contiene un puntero al objeto etiquetado, el tipo de ese objeto, el nombre de la etiqueta, el autor de la etiqueta (tagger), una fecha y un mensaje; la referencia en refs/tags apunta a ese objeto tag y no al commit. En el laboratorio creamos una etiqueta anotada y examinamos ambas capas:

git tag -a v1.0 -m "Primera versión"

cat .git/refs/tags/v1.0
# 123e8dcfe98db0ea4942cad16e589ba83cb7f6f2

git cat-file -t v1.0
# tag

git cat-file -p v1.0
# object 86007e628ea5d8d3c58cf9ecafd3b77786a44b39
# type commit
# tag v1.0
# tagger Ada <ada@example.com> ...
#
# Primera versión

El archivo de la etiqueta contiene el hash del objeto tag (123e8dc…), y este contiene a su vez el hash del commit (86007e6…). Esa capa intermedia es lo que permite añadir un mensaje, una fecha y, opcionalmente, una firma criptográfica. Pro Git añade un detalle curioso: una etiqueta puede apuntar a cualquier tipo de objeto, no solo a commits. El propio repositorio de Git etiqueta un blob con la clave pública GPG de su mantenedor, y la primera etiqueta del kernel de Linux apunta a un tree.

packed-refs: cuando las referencias dejan de ser archivos sueltos

Un repositorio con miles de etiquetas o ramas tendría miles de archivos diminutos bajo refs. Para evitarlo, git gc empaqueta las referencias en un único archivo, .git/packed-refs. En el laboratorio ejecutamos git gc y comprobamos el resultado: los directorios refs/heads y refs/tags quedaron vacíos y toda la información pasó a un único archivo de texto.

git gc
ls .git/refs/heads .git/refs/tags
# (ambos directorios vacíos)

cat .git/packed-refs
# # pack-refs with: peeled fully-peeled sorted
# 86007e628ea5d8d3c58cf9ecafd3b77786a44b39 refs/heads/main
# e12ca9e0b922e44d5d20a1192b64d6b13dc363cc refs/heads/rama
# 123e8dcfe98db0ea4942cad16e589ba83cb7f6f2 refs/tags/v1.0
# ^86007e628ea5d8d3c58cf9ecafd3b77786a44b39

La línea que empieza por ^ es la versión "pelada" (peeled) de la etiqueta anotada: indica el commit final al que lleva, para no tener que abrir el objeto tag cada vez. Por supuesto, todo esto es transparente: git branch o git tag seguirán funcionando igual, leyendo primero el archivo suelto, si existe, y después packed-refs.

De los objetos sueltos a los packfiles

Todo lo que hemos creado hasta ahora está en formato suelto (loose): un archivo comprimido por objeto. Es un formato muy simple y rápido de escribir, pero ineficiente cuando el repositorio crece. Pro Git lo ilustra con un ejemplo: si modificas una sola línea de un archivo de 22 KB, Git guarda la segunda versión completa, de nuevo con unos 7 KB comprimidos, aunque casi todo su contenido sea idéntico al de la primera. Con miles de versiones, el desperdicio sería considerable.

Qué hace git gc

La solución son los packfiles. Según la documentación del libro, Git empaqueta objetos cuando hay demasiados sueltos, cuando ejecutas git gc a mano y cuando haces push a un servidor. Un packfile es un único archivo que contiene muchos objetos; viene acompañado de un archivo de índice (.idx) con las posiciones de cada objeto dentro del pack, de modo que Git puede saltar directamente a uno concreto. Ambos se llaman pack-<hash>.pack y pack-<hash>.idx.

La documentación oficial de git-gc fija los umbrales por defecto de la ejecución automática. Cuando una operación de Git invoca gc --auto, la limpieza solo se lleva a cabo si hay más de 6700 objetos sueltos (gc.auto) o más de 50 packs (gc.autoPackLimit). El libro redondea esa cifra a "unos 7.000 objetos"; la documentación de referencia da el valor exacto. Establecer gc.auto a cero desactiva también el resto de heurísticas automáticas.

Deltas: guardar solo las diferencias

La parte inteligente del empaquetado es la compresión por deltas. Durante el empaquetado, Git busca archivos con nombres y tamaños parecidos y almacena un objeto completo (la base) y, para los demás, solo las diferencias respecto a esa base. Pro Git explica que, en el ejemplo del libro, la versión más reciente del archivo se guarda íntegra y la antigua se guarda como un delta que referencia a la nueva, con la justificación de que normalmente se necesita con más frecuencia la versión actual.

Lo comprobamos en el laboratorio. Creamos un archivo de 400 líneas, lo confirmamos, modificamos una sola línea (el archivo crece 11 bytes) y volvimos a confirmar. Antes de gc, git count-objects -v informaba de 6 objetos sueltos; después, de 6 objetos dentro de un único pack:

git gc -q
git count-objects -v
# count: 0
# size: 0
# in-pack: 6
# packs: 1
# size-pack: 2

git verify-pack -v .git/objects/pack/pack-*.idx | grep -E "blob|chain|non delta"
# 56cffe52829f6790e6a8583abe0f981a7fa137b6 blob   33611 1195 285
# 79df026f2f7869b14507329af7c78d0851cb68eb blob   18 30 1576 1 56cffe52829f6790e6a8583abe0f981a7fa137b6
# non delta: 5 objects
# chain length = 1: 1 object

Las columnas de verify-pack -v son, por orden: el hash del objeto, su tipo, el tamaño sin comprimir, el tamaño que ocupa dentro del pack, el desplazamiento dentro del archivo y, solo para los deltas, la profundidad de la cadena y el hash de la base. Aquí vemos que la versión nueva (56cffe5…, 33611 bytes) se almacena completa y ocupa 1195 bytes comprimidos, mientras que la versión antigua (79df02…) es un delta de apenas 18 bytes (30 dentro del pack) con profundidad 1 cuya base es la versión nueva. En otras palabras, la diferencia entre dos versiones de un archivo de más de 33 KB se guardó en 30 bytes. El resumen final, "non delta: 5 objects" y "chain length = 1: 1 object", indica que cinco objetos están completos y uno es un delta de un solo salto.

La base no siempre es la versión nueva. La explicación del libro describe el criterio habitual (la más reciente completa, la antigua como delta), y nuestro laboratorio lo reproduce con un archivo que crece. Pero Git decide las bases con heurísticas y no con una regla fija. En un primer intento de laboratorio, con un archivo que encogía, la base fue la versión antigua, que resultó ser la mayor de las dos (ese intento tenía además una conversión accidental de saltos de línea, así que lo descartamos como medición). No lo tomes como una regla universal: es una decisión de optimización interna, no una garantía del formato.

git gc --aggressive

La opción --aggressive merece cuidado. Según la documentación, ejecuta git repack con -f, que descarta los deltas existentes y los recalcula desde cero, y utiliza una ventana de búsqueda mucho mayor: gc.aggressiveWindow vale 250 por defecto, frente a los 10 de una búsqueda normal, y la profundidad (gc.aggressiveDepth) es de 50. El resultado puede ocupar menos espacio, pero tarda mucho más. La propia documentación aconseja no usarla sin medir antes si el ahorro compensa; para la mayoría de los repositorios, el gc normal es suficiente.

El reflog: la red de seguridad

Cada vez que HEAD o una rama cambia de posición, Git lo anota en un registro local llamado reflog, almacenado bajo .git/logs. Pro Git aclara que lo actualizan los commits, los cambios de rama y git reset, además de git update-ref. El reflog responde a una pregunta que el historial normal no puede contestar: "¿dónde estuvo HEAD antes de este cambio?".

El laboratorio crea tres commits (A, B y C), retrocede con un reset --hard y recupera todo con ayuda del reflog:

git reflog
# 1a78706 HEAD@{0}: commit: Commit C
# edc6699 HEAD@{1}: commit: Commit B
# 30347a4 HEAD@{2}: commit (initial): Commit A

git reset --hard HEAD~2
git reflog
# 30347a4 HEAD@{0}: reset: moving to HEAD~2
# 1a78706 HEAD@{1}: commit: Commit C
# edc6699 HEAD@{2}: commit: Commit B
# 30347a4 HEAD@{3}: commit (initial): Commit A

git log --oneline
# 30347a4 Commit A        (los commits B y C ya no aparecen en el log)

git reset --hard 'HEAD@{1}'
git log --oneline
# 1a78706 Commit C
# edc6699 Commit B
# 30347a4 Commit A

El reset --hard HEAD~2 hizo que B y C dejaran de ser alcanzables desde cualquier rama, pero los objetos seguían en el almacén y el reflog guardaba su posición anterior. Con HEAD@{1} (la posición de HEAD justo antes del último movimiento) volvimos exactamente al estado anterior. Este es el mecanismo que explica el consejo más repetido tras un accidente con Git: antes de dar nada por perdido, consulta git reflog.

Cuánto dura la red de seguridad

El reflog no es eterno. La documentación de git-gc establece dos plazos por defecto: las entradas del reflog caducan a los 90 días (gc.reflogExpire) y, si además la entrada ya no es alcanzable desde la punta actual, a los 30 días (gc.reflogExpireUnreachable). Una vez caducada la entrada, los commits que solo ella mantenía vivos pasan a ser objetos huérfanos, y la limpieza de objetos inalcanzables aplica su propio periodo de gracia: gc.pruneExpire vale dos semanas por defecto. El libro resume esa limpieza diciendo que git gc elimina objetos inalcanzables con antigüedad de "unos meses", lo que concuerda en orden de magnitud con la suma de plazos.

Dos matices importantes. Primero, el reflog es estrictamente local: no viaja con push ni clone, de modo que solo protege contra errores cometidos en tu copia del repositorio. Segundo, las marcas de tiempo del reflog corresponden a cuándo ocurrió el evento, así que el cálculo de caducidad depende de cuándo realizaste la operación, no de cuándo se escribió el commit. Un caso real que encontramos en el laboratorio ilustra cómo se aplican esos plazos: al fijar fechas de 2026-01-01 para los commits y ejecutar después git gc, las entradas de commit del reflog desaparecieron por tener más de 90 días respecto al momento de ejecución. Esa es una advertencia práctica para quien automatiza repositorios de prueba con fechas fijas.

Recuperar sin reflog: git fsck

Si el reflog ya no tiene la entrada, aún queda git fsck, que recorre el almacén buscando objetos inalcanzables. Para ilustrarlo creamos una rama que apuntaba a un commit, la borramos con git branch -D y caducamos el reflog con git reflog expire --expire=now --all. Con ello el commit quedó sin ninguna referencia, pero fsck lo encontró:

git branch -D recuperada
git reflog expire --expire=now --all

git fsck --lost-found
# dangling commit d9f7408eea5f2373577451e72230551c8a7c0f2e

# Para rescatarlo:
git branch recuperada d9f7408eea5f2373577451e72230551c8a7c0f2e

La etiqueta dangling (colgante) significa que el objeto existe pero nada lo referencia. Pro Git recomienda precisamente este procedimiento: localizar el commit tras la palabra "dangling commit" y crear una rama que apunte a su hash. Si, en cambio, quieres que esos objetos desaparezcan de verdad, git gc --prune=now los elimina sin esperar al periodo de gracia. En el laboratorio, el recuento de objetos en el pack pasó de 6 a 3 tras ejecutar esa orden, porque el commit colgante y los objetos que solo él referenciaba fueron eliminados.

Antes de podar, comprueba. git gc --prune=now y git reflog expire --expire=now --all son operaciones destructivas: eliminan la red de seguridad. Úsalas solo cuando estés seguro de que no necesitas recuperar nada, por ejemplo después de reescribir un repositorio para quitar un archivo enorme o una credencial filtrada.

Cuando el repositorio engorda: diagnóstico del tamaño

Un repositorio que crece sin control suele deberse a un archivo grande que se confirmó una vez y sigue existiendo en la historia aunque se borrara después. Con lo visto hasta ahora, el diagnóstico es directo. Pro Git propone un procedimiento en varios pasos que combina las herramientas que ya conocemos.

  1. Medir. git count-objects -v muestra los objetos sueltos (count y size) y los empaquetados (in-pack, packs, size-pack). Las cifras de tamaño se expresan en kilobytes.
  2. Localizar los objetos más pesados. El libro ordena la salida de verify-pack -v por la tercera columna (tamaño) y se queda con los últimos.
  3. Identificar el archivo. Con git rev-list --objects --all se obtiene la lista de objetos con su nombre de ruta, y un grep del prefijo del hash revela a qué archivo corresponde el blob.
  4. Encontrar los commits afectados. git log --oneline --branches -- ruta/al/archivo lista los commits que tocaron ese archivo.
git count-objects -v

git verify-pack -v .git/objects/pack/pack-*.idx | sort -k 3 -n | tail -3

git rev-list --objects --all | grep <prefijo-del-hash>

git log --oneline --branches -- archivo-grande.tgz

El paso siguiente, eliminar el archivo de toda la historia, reescribe todos los commits afectados y, por tanto, todos los hashes posteriores. Es una operación mucho más seria que un commit corriente. El libro la describe con git filter-branch y advierte de que es destructiva para la historia de commits; en el ejemplo del libro el tamaño empaquetado del repositorio pasa de unos 5 MB a 8 KB una vez eliminadas las referencias antiguas, el reflog y los objetos sueltos. Consulta siempre la documentación de la versión de Git que utilices antes de reescribir un repositorio compartido, y avisa a todo el equipo: cada colaborador tendrá que sincronizar su copia con la historia reescrita.

SHA-1, colisiones y la transición a SHA-256

Todo lo anterior se ha descrito con SHA-1, que sigue siendo el algoritmo de identificación en la mayoría de los repositorios. La documentación del proyecto, en el documento de diseño de la transición de función hash, explica por qué se quiere abandonar. En 2017 se demostró un ataque práctico de colisión sobre SHA-1 (el conocido como SHAttered). Git incorporó desde la versión 2.13.0 una variante endurecida de SHA-1 que no es vulnerable a ese ataque concreto, pero el documento insiste en que "SHA-1 sigue siendo débil" y que resulta prudente dejar atrás cualquier variante.

El proyecto eligió SHA-256 a finales de 2018. Los criterios fueron una longitud de 256 bits, su amplia disponibilidad en implementaciones como OpenSSL, su adecuación a las necesidades de Git en cuanto a colisiones y segundas preimágenes, y el rendimiento como criterio de desempate. Según el diseño, la migración debe poder hacerse repositorio por repositorio, sin que ninguna otra parte tenga que hacer nada, y un repositorio SHA-256 debería poder comunicarse con servidores SHA-1 mediante conversión de objetos al hacer fetch y push.

Con una versión moderna de Git puedes crear hoy un repositorio de ese tipo. En el laboratorio lo hicimos con la opción --object-format=sha256 y comprobamos el resultado:

git init --object-format=sha256 demo256
cd demo256
echo hola > a.txt && git add a.txt && git commit -m "sha256"

git rev-parse HEAD
# 941de503f5ee7b61365a7e98989e93ed06dec137ee3c5baf5e77299f28588bf0

git config extensions.objectformat          # sha256
git config core.repositoryformatversion     # 1

El identificador tiene 64 caracteres hexadecimales en lugar de 40, y el repositorio queda marcado con la versión de formato 1 y la extensión objectformat = sha256, un mecanismo para que versiones antiguas de Git se nieguen a abrirlo en lugar de interpretarlo mal, tal como describe el documento de diseño. Eso significa también que un repositorio SHA-256 no puede ser leído por versiones antiguas de Git, que no se admiten clones superficiales ni alternos en la propuesta original y que el documento desaconseja explícitamente alojar repositorios SHA-256 en servidores públicos mientras el protocolo de Git no incorpore soporte para ese formato.

Qué no sabemos (y por qué importa). El documento de diseño está redactado en futuro condicional: describe un plan y no indica qué partes están implementadas en cada versión ni establece una fecha para que SHA-256 sea el formato por defecto. Por eso este artículo no afirma que lo sea. Si necesitas saber qué soporta tu versión concreta de Git, consulta sus notas de versión y su documentación, y comprueba también qué soporta tu plataforma de alojamiento.

Errores y malentendidos frecuentes

Conocer el modelo interno permite desmontar varias creencias populares que a menudo causan problemas.

"Git guarda diferencias entre versiones"

No en el modelo lógico. Cada commit apunta a una instantánea completa del proyecto (un tree raíz). Los deltas son un detalle de almacenamiento del packfile, invisible para los comandos de alto nivel y decidido por heurísticas de compresión. Que un objeto esté almacenado como delta no cambia nunca su identificador ni su contenido lógico.

"Borrar una rama borra sus commits"

Borrar una rama elimina un archivo de referencia. Los commits siguen en el almacén y, mientras exista una entrada de reflog que los alcance, pueden recuperarse con git branch <nombre> <hash>. Pasados los plazos de caducidad y una limpieza, desaparecen de verdad.

"Un rebase modifica mis commits"

Un rebase no modifica ningún objeto, porque los objetos son inmutables. Crea commits nuevos con contenido parecido y mueve la rama. Los antiguos quedan huérfanos y recuperables vía reflog. Gracias a eso, el reflog (y la referencia ORIG_HEAD que Git deja antes de operaciones como el rebase) permiten volver a la posición anterior si algo sale mal; si te interesa ese flujo completo, lo desarrollamos en el artículo sobre rebase interactivo.

"El reflog me protege del servidor"

El reflog es local. Si alguien fuerza un push --force que sobrescribe una rama en el servidor, el reflog del servidor (si lo mantiene) no es el tuyo, y los commits perdidos solo se recuperan si tú los tenías en tu copia. Por eso, antes de forzar un push, conviene entender qué commits quedarán sin referencia en el remoto.

"git gc solo ocupa tiempo"

Un gc periódico mantiene el rendimiento: reduce el número de archivos sueltos, empaqueta referencias y genera packs con deltas. En equipos grandes, las plataformas de alojamiento lo ejecutan en segundo plano; en local, Git lo lanza automáticamente cuando se superan los umbrales que hemos visto. Desactivarlo (gc.auto=0) solo tiene sentido en situaciones controladas, como el laboratorio de este artículo, donde queríamos observar el estado antes y después de empaquetar.

Una receta para explorar cualquier repositorio

Con todo lo anterior puedes diseccionar un repositorio real. La siguiente secuencia no modifica nada y te permite recorrer la estructura desde la rama hasta el contenido de un archivo:

# 1. ¿En qué rama estoy y a qué commit apunta?
git symbolic-ref HEAD
git rev-parse HEAD

# 2. ¿Cómo es ese commit?
git cat-file -p HEAD

# 3. ¿Cómo es el directorio raíz?
git cat-file -p HEAD^{tree}

# 4. ¿Cuál es el contenido de un archivo concreto en ese commit?
git cat-file -p HEAD:README.md

# 5. ¿Cuántos objetos hay y cómo están almacenados?
git count-objects -v

# 6. ¿Qué referencias existen?
git for-each-ref

La notación HEAD^{tree} resuelve el tree del commit apuntado por HEAD, y HEAD:README.md resuelve directamente el blob de ese archivo en ese commit. Con estas dos expresiones basta para navegar el modelo de datos completo sin salir de la terminal.

Preguntas frecuentes

¿Por qué el hash cambia si solo modifico el mensaje del commit?

Porque el mensaje forma parte del contenido del objeto commit y el hash se calcula sobre todo el contenido. Cambiar el mensaje con commit --amend produce un commit nuevo con otro identificador, y los commits posteriores que lo tuvieran como padre dejarían de coincidir.

¿Dos archivos idénticos ocupan el doble?

No. Al tener el mismo contenido tienen el mismo hash y comparten un único blob. Los dos nombres aparecen como entradas distintas del tree, pero apuntan al mismo objeto.

¿Puedo ver el contenido de un objeto con un editor de texto?

No directamente, porque los objetos sueltos están comprimidos con zlib. Se pueden leer con git cat-file -p o, como hicimos arriba, descomprimiendo el archivo con cualquier herramienta capaz de leer zlib.

¿Qué diferencia hay entre HEAD~1 y HEAD^?

Para un commit con un solo padre son equivalentes. Se distinguen en los commits de fusión: HEAD^2 es el segundo padre, mientras que HEAD~2 es el abuelo siguiendo siempre el primer padre.

¿Cuánto tiempo tengo para recuperar un commit tras un reset?

Depende de los plazos de caducidad configurados. Con los valores por defecto documentados, las entradas del reflog duran 90 días, o 30 si ya no eran alcanzables, y los objetos sueltos inalcanzables tienen además un periodo de gracia de dos semanas antes de poder ser podados. En la práctica, cuanto antes revises el reflog, mejor.

¿Es seguro ejecutar git gc en cualquier momento?

El gc normal es una operación de mantenimiento pensada para ejecutarse sin riesgo; respeta los periodos de gracia antes de eliminar nada. Lo peligroso son las variantes que acortan esos plazos a cero, como --prune=now, o que reescriben mucho trabajo, como --aggressive en repositorios enormes.

¿Las etiquetas y las ramas se comportan igual?

Ambas son referencias, pero una rama avanza cuando haces commit estando en ella, mientras que una etiqueta se queda siempre apuntando al mismo objeto salvo que la muevas explícitamente. Las etiquetas anotadas, además, son objetos con autor, fecha y mensaje.

¿Qué pasa con los submódulos?

Un submódulo se registra en el tree con un modo especial y apunta a un commit de otro repositorio en lugar de a un blob o a un tree. Es un tipo de entrada distinto de los tres modos de archivo vistos aquí, y por eso Pro Git señala que los modos de archivo válidos para blobs son solo tres.

Conclusión

Git parece complejo desde fuera, pero por dentro se reduce a una idea y tres estructuras. La idea es el direccionamiento por contenido: cada objeto se identifica por el hash de lo que contiene. Las estructuras son los objetos inmutables (blob, tree, commit y tag), las referencias mutables que les ponen nombre (ramas, etiquetas, HEAD) y la maquinaria de mantenimiento (packfiles, reflog y recolección de basura) que mantiene todo eficiente y recuperable.

Entender esas piezas cambia la forma de usar Git. Un reset --hard deja de dar miedo porque sabes que el reflog guarda la posición anterior; un rebase deja de ser magia porque sabes que produce commits nuevos; un repositorio gigante deja de ser un misterio porque sabes cómo medirlo y qué comandos revelan qué objeto lo infla. Y, sobre todo, aprendes a desconfiar de las explicaciones simplificadas: Git no guarda diferencias, no borra al borrar una rama y no "modifica" commits. Lo que hace es mucho más elegante: añade objetos nuevos, mueve punteros y limpia más tarde lo que nadie referencia.

Si quieres seguir explorando, te recomendamos reproducir los experimentos de este artículo en un directorio de pruebas y complementarlos con la lectura de los capítulos de Pro Git sobre el funcionamiento interno. Y si trabajas con automatizaciones, el artículo sobre caché en GitHub Actions muestra cómo el mismo principio de direccionamiento por contenido (el hash de un archivo de bloqueo) se usa para decidir si una caché es válida.
